# 사용자 세션 입력·배터리 보호와 활성 요청 관측

2026-10-01 · 빌드 50 미배포 후보. 사용자 소유 일반 작업 세션을 보완했다. 설치본은 빌드 49이며 실제 덮개·전원 조작, 전역 전원 값, 잠금 정책, 관리자 도우미 설치는 이번 단계에서 변경하지 않았다.

## 수정한 동작

수동 시작·연장, 자동 트리거 켜기, 보호 뒤 재개 직전에 전원·발열·full wake·배터리 잔량·GUI 권한을 다시 읽는다. 이전 3초 주기 표본이 AC였다는 이유로 현재 배터리에서 무제한을 시작하거나, 새 보호 사유를 건너뛰지 않는다. 관측 불가 값은 정상으로 대체하지 않는다. 이미 종료된 조정자는 재사용하지 않는다.

배터리에서 잔량이 없거나 범위를 벗어나면 시작을 거부한다. 실행 중인 세션의 잔량 관측이 사라지거나 하한에 도달하면 자체 요청을 해제하고 보호 중지를 남긴다. 배터리 보호 재개는 하한보다 5% 높은 잔량을 요구한다. AC에서 배터리 잔량이 없다는 이유로 데스크톱의 일반 작업을 차단하지 않는다.

AC의 무제한 선택은 유한한 OS 요청을 갱신하는 기존 90초 건강 확인 계약을 유지한다. 배터리는 최대 2시간이며 이전 설정의 더 엄격한 시간·잔량 제한도 적용한다. UI의 직접 입력 상한과 실제 집행에서 같은 제한을 사용한다. 자동 트리거 선택과 수동 세션 종료는 독립적으로 유지한다.

## 설정 이관

사용자 환경설정의 `userOwnedSessionSettings`는 v1에서 v2로 이관한다. 지원 가능한 v1의 사용 여부·자동 선택·보호 중지·같은 부팅의 소비된 배터리 예산을 보존한다. 실행 중인 세션과 마감 시각은 저장하거나 되살리지 않는다.

변환 전 원본 바이트는 `userOwnedSessionSettings.migration.v1.backup`에 남긴다. 서로 다른 원본이 이미 있으면 UUID를 붙여 별도로 보존한다. 일반 저장의 `.backup`과 구별하며 미래 버전·손상 데이터·예상하지 못한 v1 제한은 추측으로 변환하지 않는다. 유효한 기존 `Control`을 전달받은 경로에서는 잔량·시간 제한만 이어받으며 폐기한 섭씨 제한을 재도입하지 않는다. root `Control` schema 3과 IPC protocol 2는 이번 수정으로 변경하지 않았다.

## 실제 API에서 발견한 빈 목록 처리

기존 native 검사에서 요청 level을 0으로 바꾼 뒤 활성 목록 확인이 실패했다. 최초 원본 관측은 `IOPMCopyAssertionsByProcess`의 성공 코드와 NULL 출력, 자체 속성 level 0이었다. 이것은 비활성 요청이 목록에 계속 보인다는 증거가 아니었다.

[Apple IOKit 공개 구현](https://raw.githubusercontent.com/apple-oss-distributions/IOKitUser/main/pwr_mgt.subproj/IOPMAssertions.c)은 빈 프로세스 배열에서 출력 dictionary를 만들지 않고 반환하는 경로를 갖고 있다. 같은 구현의 내부 조회는 일부 실패에서도 성공 코드를 반환할 수 있어 성공 코드와 NULL만으로 요청 없음을 단정하지 않는다. 현재 SDK의 `IOPMCopyAssertionsStatus` 계약과 실제 응답을 함께 확인했다.

`PowerAssertionSnapshot`은 정상 dictionary를 그대로 읽고, 성공 코드와 NULL이면 별도 집계를 조회한다. 요청 진단은 네 가지 표시 대상 종류가 모두 0인지, 자체 idle 요청은 해당 idle 종류가 0인지 확인한다. `EnableIdleSleep`처럼 그 판단 대상이 아닌 집계는 절전 방지 요청으로 취급하지 않는다. 집계 실패·NULL·형식 오류·누락·관련 종류의 활성 값은 미확인으로 남긴다. malformed한 비NULL 목록을 집계로 우회하지 않는다. 자체 ID·PID·종류 신원 검증도 유지한다.

## 실행 근거

| 검사 | 결과와 범위 |
|---|---|
| 누락된 배터리 입력의 수정 전 회귀 | 새 2개 검사에서 5개 assertion 실패. 잔량 없이 시작·유지가 되는 경로를 재현 |
| 입력·배터리 보호·이관·종료 수명 | Core 6개와 앱 조정자 7개를 추가. 실제 잔량 감소·과열 조작은 아님 |
| 활성 목록 교차 관측 | 9개 회귀. 실패/손상/관련 활성 값은 계속 미확인, 관련 요청이 모두 꺼진 관측은 빈 목록으로 판정 |
| 관련 native·관측 검사 | 25개 통과. 전체 실행에도 포함되므로 합산하지 않음 |
| 전체 Swift, native 옵션 포함 | Core 437개 + 업데이트/앱 30개 = 467 통과, 0 건너뜀, 0 실패 |
| 실제 OS assertion 검사 | 전체 467개에 포함된 6개. 자체 요청 관측·TurnOff 만료/재사용·다른 caffeinate 요청 보존을 확인 |
| 로컬 배포 후보 | macOS 15 arm64 앱·helper·복구 실행기·CLI 빌드 성공. 서명·리소스 일치·읽기 전용 설치 판정·격리 도우미 소켓·CLI resume/stop 검사 통과. 운영 설치·배포와 구별 |

새 앱 조정자의 native 보호 검사는 실제 GUI 권한과 OS assertion을 사용하되 전원·잔량·발열 입력은 주입했다. 모의 배터리 하한 이후 자체 요청 해제와 별도 `caffeinate` 요청의 생존을 확인한 결과다. 단위 이관은 별도 UserDefaults 도메인의 읽기·원본 백업·같은 부팅 예산을 확인한 것이며, Sparkle 전체 업데이트나 프로세스 강제 종료 시 저장 내구성의 증거로 확대하지 않는다.

native 만료 검사는 짧은 시험 요청을 사용한다. 전체 정상 동작·hang에서 90초 보호 상한, 실제 패널 꺼짐·잠금·물리 Sleep, 모든 Apple Silicon 기기의 성공을 증명하지 않는다. 관련 [D-05/D-07 한계](DESIGN-GAPS.ko.md)는 유지한다.

## 남은 범위

현재 `AppModel`은 확인된 데스크톱에서 이 사용자 세션 실행기를 선택한다. MacBook의 일반 작업·덮개 조정자 통합, 부분 센서 관측 실패에서도 일반 기능을 제공하는 라우팅 및 CLI의 공통 집행은 후속 과제다. 이 정책의 배터리 회귀 통과를 설치된 MacBook의 root 경로 통과라고 부르지 않는다.

실제 macOS 15 런타임, 데스크톱·UPS·독, 사용자 전환, 원격 화면·입력, 실제 보호 해제 지연과 닫힌 전원 연결은 별도 시험이 남아 있다. 설치본 교체, Sparkle UI → 재시작 → 관리자 도우미 교체, 커밋·푸시·원격 CI·릴리스 게시도 완료 전이다. 컴퓨터유즈로 게시한 [#6 검증 기록](https://github.com/jukqaz/tether/issues/6#issuecomment-5919953898)과 [GitHub 작업 관리](GITHUB-WORKFLOW.ko.md)에서 이슈를 진행 중으로 유지한다.
