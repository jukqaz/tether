# macOS·다른 앱 공존 검증 — 빌드 40–41

2026-09-28, Apple Silicon Mac / macOS 27.0 (26A428). 실제 잠자기나 화면 꺼짐을 유발하지 않고, 정책·실제 도우미·실제 OS 요청 조회를 분리해 검증한다. macOS 26의 전체 실기기 동작과 모든 독·앱 버전 조합까지 확인한 결과는 아니다.

## 이번에 고친 경계 상황

1. **보호 요청 뒤 덮개 열기:** 발열·센서 문제로 잠자기를 요청한 뒤 덮개를 열어도 이전 20초 요청이 남아 재요청했다. 실제 도우미의 dry-run에서 두 원인 모두 재현했다. 사용자 직접 잠자기, 닫힌 덮개 유지 종료, 보호 중지의 의도를 구분하고 첫 호출·각 재시도·마지막 대체 명령 전에 현재 상태를 재확인한다.
2. **잠자기 요청 취소:** 실패한 잠자기의 재시도 중 사용자가 다시 켜기를 눌러도 기존 재시도가 남았다. 명시적인 재개가 성공하면 기존 요청·재시도를 취소한다. 다른 주체의 전역 override가 있으면 직접 잠자기도 `powerConflict`로 안내하고 그 값을 해제하지 않는다.
3. **macOS 잠자기 진입:** `SystemWillSleep` 이후 일반 관측이 잠시 Full Wake로 남아 있을 수 있다. 그 사이 설정·전원·타이머 이벤트가 와도 잠자기 방지를 다시 획득하지 않는다. OS 깨어남 통지와 Full Wake를 확인한 뒤 정상 평가한다.
4. **감시 장치의 복구 경합:** 이미 해제된 전역 값에 오래된 소유 기록이 남으면 이후 타 앱의 변경을 자신의 것으로 오인할 수 있었다. 오래된 기록을 소비하고, 새 도우미가 기록을 준비한 직후에는 첫 상태 게시를 기다린다. 복구 도중 기록 내용이 바뀌었으면 새 기록을 보존하고 잠자기 요청을 생략한다.

감시 장치의 새 소유 기록에는 기존 heartbeat와 같은 90초 관측 여유를 적용한다. 이 시간은 앱의 복구 정책이며 제조사 인증 시간이나 USB-C 장치 전환 보증이 아니다.

조합 수는 단위 테스트 내부의 반복 조건 수다. 28,800개의 서로 다른 기능이나 물리 기기를 검사했다는 뜻이 아니다. 마지막 서비스 명령 수정 후에는 도우미 빌드와 두 통합 묶음을 다시 실행했다. 핵심 정책·감시 장치의 단위 검사는 해당 소스 수정 후 실행했다.

### 주요 합격 조건

- AC의 외장·가상·혼합·확인 불가 화면에서 정상 설정 전환이 추가 `disablesleep 1`, 전체 화면 끄기, 시스템 잠자기를 만들지 않는다.
- 다른 주체가 가진 전역 override를 해제하거나 반복 적용하지 않는다.
- Dark Wake·전원 확인 불가 상태에서 새 유지·화면 끄기·자동 시스템 잠자기를 시작하지 않는다.
- 실패한 자동 잠자기의 재시도 중 덮개 열림, native 화면 연결, Dark Wake, 전원 불명, 타 앱 override가 생기면 중단한다.
- 직접 잠자기는 최대 20번 시도한 뒤 대체 요청 한 번으로 제한한다. 조건이 사라지면 대체 요청도 생략한다.
- 이미 켜져 있던 저전력 모드, 원래의 고성능 모드, 이후 타 앱이 고른 모드를 구분한다. 배터리와 AC 설정을 각각 검증한다.
- 화면 켜짐 요청과 작업 유지 요청을 구분한다. 화면을 끄려는 현재 의도와 반대일 때만 상충으로 표시한다.
- 기존 과열·센서·배터리 보호가 사라지지 않는다. 명시적으로 AC 보호를 켠 닫힌 native 클램쉘에서 critical 중지는 기본 통합 검사로 유지한다.

## 실제 macOS에서 한 검사

`LivePowerAssertionTests`는 테스트가 소유한 IOKit 유휴·화면 절전 방지 요청을 만든 뒤 앱과 같은 `SystemProbe`로 읽는다. 요청은 10초 뒤 자동 해제되도록 설정하며 정상 경로에서도 즉시 해제한다. `caffeinate -i -t 10`은 이 테스트가 띄운 별도 프로세스다. 자신의 요청을 해제한 뒤에도 그 프로세스의 요청이 남아 있음을 확인한다. 사용자의 기존 앱 요청을 해제하지 않는다.

검사 시점의 공용 UI 읽기 모듈에서 **Amphetamine, Splashtop Streamer의 시스템·화면 유지 요청**을 실제로 관측했고, 실행 중인 앱으로 연결했다. 요청의 이름/설명 원문은 제거되었음을 확인했다. 이때 비교용 `displaySleepExpected=true`를 주었으므로 ‘실제 현재 화면 충돌’이나 ‘LLM 추론 중 물리 호환성 통과’라는 뜻은 아니다.

실제 LLM 앱의 전체 추론 흐름을 대신 실행한 것은 아니다. Electron의 `prevent-app-suspension`은 화면 꺼짐을 허용하고 `prevent-display-sleep`은 화면을 유지하므로, 앱 이름보다 활성 요청 종류를 기준으로 검증한다. [Electron 공식 문서](https://www.electronjs.org/docs/latest/api/power-save-blocker), [Apple IOKit 요청](https://developer.apple.com/documentation/iokit/kiopmassertiontypepreventuseridlesystemsleep).

macOS native 클램쉘은 외장 화면과 입력 장치의 연결 승인 상태에도 영향을 받는다. 이를 Tether가 임의로 변경하거나 완전히 대체하지 않는다. [Apple 주변기기·닫힌 덮개 안내](https://support.apple.com/en-us/102282).

## 재현 명령

```sh
swift build
TETHER_RUN_LIVE_ASSERTION_TESTS=1 swift test
python3 scripts/test-service.py
python3 scripts/test-conflicts.py
python3 scripts/test-upgrade.py
python3 scripts/test-uninstall.py
```

일반 `swift test`에서는 실제 IOKit 요청 생성 4개를 skip한다. CI에는 기본 검사와 충돌 통합 검사를 등록했다. CI 등록은 원격 CI 실행 완료의 증거가 아니다. dry-run에서는 실제 전원/덮개 알림도 구독하지 않아 테스트 중 사용자의 물리 조작이 모의 시나리오에 섞이지 않는다.

## 시뮬레이션의 경계

덮개를 직접 닫지 않아도 제어 흐름·오류·재시도·복구는 재현할 수 있다. 그러나 실제 내장 패널 전원, 물리 잠자기/깨어남, 특정 독·KVM·DisplayLink와의 동작, 장시간 배터리 비용은 해당 장치에서 별도로 관측해야 한다. 높은 온도를 일부러 유발할 필요는 없다.

`SleepDisabled`는 macOS의 공유 전역 값이며 배타적 소유권이나 원자적 비교 후 변경 API가 없다. 여러 도구가 같은 값을 동시에 쓰거나 관측 사이에 값을 바꿨다가 되돌리면 변경 주체를 완전히 구별할 수 없다. 소유 기록·직전 관측·변경 감지 시 중지로 충돌을 줄이지만 **모든 타 앱 조합에서 충돌 0을 보증하지 않는다**. 같은 종류의 전역 클램쉘 제어는 한 도구에서만 활성화하고, LLM·다운로드 앱의 일반 유휴 절전 방지는 별도 요청으로 공존시키는 구성이 가장 명확하다.

## 배포 전 빌드 41 재검증

빌드 41은 설치 안내·CLI 표현·배포 채널과 소스 식별 정보를 정리한 베타다. 전원 정책은 빌드 40과 같다. 281개 단위 검사(실제 IOKit 4개 포함), 70개 기본 통합, 55개 충돌 시나리오, 4개 설치·복구, 7개 제거 검사를 다시 통과했다. 별도 합성 앱의 실제 Sparkle 엔진 업데이트 성공과 ZIP/피드 변조 거부도 3개 모두 통과했다.

배포 검사는 실제 ZIP을 다시 풀어 체크섬·중첩 코드 서명·앱/도우미 빌드·아키텍처·서명된 피드를 확인하고 포장된 도우미와 CLI로 dry-run 통신을 검사한다. 이는 설치기/launchd나 물리 잠자기 검증과 구분한다. `--require-clean`은 미커밋 소스에서 만들어진 파일의 게시를 거부한다.

현재 서명은 ad-hoc, 공증은 없으며 Gatekeeper 자동 승인은 실패한다. 회사 기기의 수동 허용 및 관리자 설치 가능 여부는 대상 기기의 정책에 달려 있다. [설치·실기기 시험](INSTALL-AND-TEST.ko.md) · [배포 절차](RELEASING.ko.md).
