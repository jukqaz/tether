## 1. 결론과 범위

자동 AC 전용, 모든 AC→배터리 전환에서 기존 요청 종료, 배터리 수동 최초 시작+120분 상한, 종료된 수동의 부활 금지는 서로 일관된다. 기본 F-01~12와 확장 E01~22의 식별자 누락도 없다. **핵심 전원 계약 자체의 직접 모순은 확인하지 못했다.**

다만 남은 요청의 소유 범위, 옵션 합성, 장애·종료 수명과 기본값이 충분히 정의되지 않았다. 이대로 구현하면 같은 문장을 서로 다르게 해석할 여지가 있다. 다음 P1은 그 해석에 따라 전원 분리 종료가 생략되거나 잘못된 요청이 살아남을 수 있는 항목이다. P2는 설정 손실·잘못된 표시·사용성 문제를 막기 위한 항목이다. 런타임 결함이 재현됐다는 뜻은 아니다.

## 2. 먼저 보완할 규칙

### R-01 · P1 · ‘다른 유지 요청’이 Tether 요청인지 타사 요청인지 불명확

- **근거:** §4.2 136행은 다른 유지 요청이 남으면 Mac Sleep을 요청하지 않는다고 한다. §4.1 120행과 §8 226행은 자체 자원과 타사 요청을 구분한다.
- **문제 상황:** 닫힌 채 AC를 분리했고 Tether 요청은 모두 끝났지만 원격 앱의 유휴 assertion이 남아 있다. 이를 ‘다른 유지 요청’으로 해석하면 Tether가 분리 후 Sleep 요청 자체를 생략할 수 있다.
- **추천:** 종료 예외의 ‘다른 요청’은 **종료 사건 이후에도 유효한 Tether 요청**으로 한정한다. 분리 이전의 Tether 요청은 모두 소비한다. 타사 요청의 존재만으로 선택된 분리 종료를 생략하지 않고, 타사 자원은 변경하지 않는다. 실제 Sleep이 막혔거나 확인되지 않으면 그 결과와 관측 근거를 따로 표시한다.
- **확인 기준:** 타사 유휴 요청이 있는 닫힌 분리에서도 자체 원복과 선택된 Sleep 요청을 시도한다. 타사 전역 차단 해제나 실제 Sleep 성공을 보장하지 않는다. 새 유효 수동 요청이 먼저 승인되면 과거의 미실행 Sleep은 취소한다.

### R-02 · P1 · 프리셋 개수와 전역·요청별 화면/덮개 옵션의 우선순위 누락

- **근거:** §5.2 173~177행은 프리셋 저장·적용과 다른 요청 보존을 설명하지만 동시에 활성인 프리셋 수, 전역 OFF와 프리셋 ON의 관계는 정하지 않았다. §7 199행의 화면 해제도 요청별이다.
- **문제 상황:** 프리셋 A는 화면 유지 OFF, 실행 중 수동 B는 ON인데 전역 화면 유지를 끈 경우 최종 결과가 명확하지 않다.
- **추천:** 자동 설정 프리셋은 **한 번에 하나만 적용**한다. 여러 조건은 그 안의 AND/OR로 표현한다. 저장한 프리셋을 독립 실행기로 늘리지 않는다. 전역 화면/덮개 OFF는 실행 허용의 상한이며, ON은 강제 실행이 아니다. 허용된 범위에서 유효한 요청 중 하나라도 해당 기능을 요구하면 유지한다. 요청별 OFF·유휴 후 화면 해제는 그 요청에만 적용한다.
- **확인 기준:** 프리셋 적용은 자동만 즉시 재평가하고 현재 수동의 시간·선택은 보존한다. 다만 사용자가 전역 허용을 직접 끄거나 보호가 발동하면 실제 해당 기능은 해제된다. 설정값 보존과 실행 상태를 구분해 표시한다.

### R-03 · P1 · 수동 유지 중 새 명령/PID 작업을 시작했을 때의 결과 누락

- **근거:** §3.2 85행과 §6.1 184~185행은 수동 하나·중복 시작으로 시간 초기화 금지만 정한다.
- **문제 상황:** 기존 30분 수동 중 짧은 명령을 실행했을 때 새 작업을 기존 수동에 붙이면, 그 명령 종료가 원래 30분 작업까지 끝낼 수 있다. 교체·거절·무시 중 어느 결과인지도 정해지지 않았다.
- **추천:** 기존 수동이 활성일 때 새로운 수동/PID 작업 요청은 **명확히 거절**하고 기존 기한·연결 대상을 보존한다. 동일 명령의 재전송은 원래 결과만 돌려주고 새 요청으로 만들지 않는다. 교체·작업 합치기는 이번 범위에 추가하지 않는다.
- **확인 기준:** 거절을 성공으로 표시하지 않는다. 유지가 승인되지 않은 작업을 새 CLI가 임의로 실행하지 않는다. 이미 실행 중인 외부 PID에는 영향을 주지 않는다. 기존 작업을 끝내고 새 작업을 시작하는 조작은 별개다.

### R-04 · P1 · 필수 관측의 범위와 unknown을 거친 전원 전이 누락

- **근거:** §4.3 149행과 §5.1 159행은 미확인·공통 필수 조건을 구분하지만 상태별 범위가 없다. §7 209행은 필수 관측 실패 뒤 명시적 재개를 요구한다.
- **문제 상황:** `AC → 미확인 → 배터리`에서 마지막 AC를 잊으면 분리 사건을 놓칠 수 있다. 반대로 일정 권한 실패를 필수 관측 실패로 처리하면 정상 수동까지 중단된다.
- **추천:** 마지막으로 확인한 전원과 현재 관측의 유효성을 따로 둔다. `AC → 미확인 → 배터리`는 기존 요청을 한 번 소비하고, `AC → 미확인 → AC`는 가짜 분리/새 연결로 만들지 않는다. 전원·열·소유자 같은 공통 관측, 도우미/덮개 관측, 개별 자동 조건을 나눈 적용표를 명세에 추가한다. 개별 조건 오류는 그 조건에만 적용한다.
- **확인 기준:** 심각/위험 열 상태와 확인된 분리는 유예하지 않는다. 보호 중지로 확정해 끝낸 수동은 관측 회복만으로 부활하지 않는다. 분리와 관측 실패를 모두 기록한다. 미확인 구간을 정상 유지·원복 성공 증거로 사용하지 않는다.

### R-05 · P1 · 도우미 미준비·구버전·통신 단절·실제 종료의 처리 차이 누락

- **근거:** §1 15행은 MacBook 도우미 필수 준비를, F-04는 실행 확인을, §7 209행은 관측 실패를 규정한다. 각 실패에서 수동 수명과 실행 범위를 얼마나 중단하는지는 없다.
- **추천:** MacBook 필수 준비 정책을 유지하면서 설치 상태·프로토콜 호환·연결·실제 덮개 실행을 별도 상태로 둔다. 통신 시간 초과를 도우미 사망 또는 원복 완료로 단정하지 않는다. 확인할 수 없는 덮개 허가는 새로 만들거나 갱신하지 않고, 기존 허가는 유한한 기한과 감시 장치로 회수한다. 보호 중지로 확정한 요청은 종료하고 명시적 재개를 요구한다.
- **보완할 구분:** 일시적 통신 실패 동안 아직 유효한 일반/화면 요청을 보존할 수 있는 조건과, 전체 보호 중지로 전환할 조건을 실행 설계에서 명시해야 한다. 살아 있는 요청의 새 실행 확인과 이미 종료된 요청의 부활을 구분한다. 구버전에서 일부 기능만 거절됐을 때 기존 정상 기한을 줄이거나 연장 성공으로 표시하지 않는다.
- **확인 기준:** 설치 거부·구버전·응답 지연·실제 프로세스 종료를 각각 다룬다. 연결 없는 앱이 즉시 원복됐다고 표시하지 않는다. 재접속의 옛 ACK/허가가 종료 상태를 되돌리지 않는다.

### R-06 · P1 · 앱 종료·교체 업데이트·사용자 전환의 수명 계약 부족

- **근거:** §3.2 88~89행과 §4.3 144행은 종료된 수동 복원 금지·소유자 종료를 정하지만 종료 시점, 업데이트 취소, 빠른 사용자 전환의 결과는 없다.
- **추천:** 정상 종료는 자체 요청 종료와 원복을 수행하고, 비정상 종료는 남은 허가가 유한 기한 안에 회수되게 한다. 업데이트 확인·다운로드·아직 앱이 살아 있는 교체 취소만으로 정상 작업을 끝내지 않는다. **실제 종료/교체에 들어가면 수동을 소비**하고 새 프로세스에서 복원하지 않는다. 새 실행은 기존 원복 기록·호환성을 확인한 뒤 허용된 AC 자동만 평가한다.
- **소유자 추천:** 빠른 사용자 전환은 활성 소유자 변경으로 취급해 이전 사용자의 실행 권한을 정리한다. 돌아온 사용자의 수동은 부활하지 않는다. 단순 잠금·원격 연결은 사용자 전환으로 취급하지 않는다.
- **확인 기준:** 업데이트 취소 전후, 앱 강제 종료, 이전 앱과 새 앱의 동시 실행, A→B→A 전환, 실제 OS Sleep→FullWake를 구분한다. 실제 Sleep의 수동 소비는 이미 확정 요구이며 새로 결정할 항목이 아니다.

### R-07 · P1 · 데스크톱의 ‘해당 없음’과 관측 실패 구분 부족

- **근거:** §1 14~18행은 데스크톱 지원·기능 확인을 규정하지만 §5.1 159행과 §7 207~209행의 공통 보호에 내장 배터리/덮개가 없을 때의 적용표는 없다.
- **추천:** 덮개·내장 배터리가 없는 데스크톱은 해당 기능을 `해당 없음`으로 처리한다. 배터리 센서가 없다는 이유로 일반 작업을 보호 중지하거나 도우미 설치를 요구하지 않는다. UPS·출처 미확인은 검증 없이 정상 AC로 간주하지 않고 지원되는 전원 분류를 별도로 명시한다.
- **확인 기준:** 데스크톱·MacBook·내장 배터리 관측 실패·외부 전원 출처 미확인을 다른 입력으로 검증한다. 모든 Apple Silicon 기종에서 같은 센서가 있다고 가정하지 않는다.

### R-08 · P2 · 가져오기에서 적용 전 차이·이름 충돌·활성화 범위 누락

- **근거:** 보조 확장안 E14는 적용 전 차이를 요구하지만 v4 §8 232~234행은 전송 대상과 보존만 규정한다.
- **추천:** 가져오기는 먼저 차이·지원 안 되는 조건·필요 권한을 보여준다. 기본은 **비활성 복사본 추가**이며 같은 이름은 구분해서 보존한다. 전역 옵션 교체는 항목별 명시 적용으로 나눈다. 현재 수동·전체 중지·보호·활성 권한은 가져오기로 변경하지 않는다.
- **확인 기준:** 가져오기/미리보기만으로 자동 ON·수동 시작·보호 해제가 발생하지 않는다. 손상/미지원 버전은 부분 덮어쓰기 없이 오류를 설명한다. 기존 설정 원본은 보존한다.

### R-09 · P2 · 기존 앱 기본 설정이 정식 기능 목록에서 빠짐

- **근거:** `DESIGN.md` 55행과 현재 `SystemPage.swift` 26~34·216행에는 로그인 시작·언어·업데이트 자동 확인이 있다. `UpdateSettingsCard.swift` 45~54행은 정식/베타 채널, `NotificationSettingsView.swift` 16~36행은 OS 권한 상태·설정 이동을 제공한다. v4는 유지/제거 여부를 명시하지 않는다.
- **추천:** 로그인 시 시작 ON/OFF, 언어(macOS/한국어/영어), 업데이트 확인·채널, OS 알림 권한 확인/설정 이동을 유지 기능으로 명시한다. 로그인 시작은 앱 실행만 설정하고 자동 ON이나 수동 시작을 대신하지 않는다. 업데이트 채널 변경으로 설치본을 강등하지 않는다.
- **확인 기준:** 언어·로그인 설정 변경은 현재 작업 마감을 바꾸지 않는다. 알림 거부/집중 모드에도 보호는 동작하며, 권한을 나중에 켜도 오래된 종료 알림을 재생하지 않는다.

### R-10 · P2 · 종료 알림의 범위와 작업 완료 판정 부족

- **근거:** §8 217~220행·D-05는 시간 만료를 우선하고 PID 완료/실패 범위는 보류한다.
- **추천:** 기본 OFF를 유지하고 **시간 만료 / 명시적으로 연결한 작업 종료**를 선택 제공한다. 자동 조건 변화마다 알리지 않는다. 직접 실행해 종료 코드를 받은 명령은 결과를 설명할 수 있지만, 외부 PID가 사라졌다는 사실은 ‘프로세스 종료’이며 성공·실패 증거로 쓰지 않는다. 보호 알림의 기존 선택은 별도로 보존한다.
- **확인 기준:** 작업 종료·취소·만료·관측 실패를 구분하고, 다른 AC 유지가 남으면 함께 설명한다. 알림 때문에 원복이나 Sleep을 늦추지 않는다. 이것은 기존 D-05보다 범위를 넓힌 **새 추천**이며 아직 채택하지 않았다.

### R-11 · P2 · 새 설치·일부 선택 기능의 초기 상태와 경계 누락

- **근거:** §1 32행에는 시간/연장/고급 조건 기본값이 있으나 새 설치의 자동·덮개 선택은 없다. §7 207행의 저전력 모드 ‘진입 시’는 시작 때 이미 모드가 ON인 경우를 정하지 않았다.
- **추천:** 새 설치는 실행 요청 없음·자동 OFF·덮개 유지 OFF에서 준비를 시작한다. MacBook 필수 준비 뒤 사용자가 AC 자동을 명시적으로 켠다. 기존 설치의 ON/OFF는 이관 규칙대로 보존한다. 저전력 모드 종료 옵션은 기본 OFF이고, 사용자가 켰다면 이미 모드가 ON인 배터리 수동 시작도 허용하지 않는 같은 조건으로 취급한다.
- **확인 기준:** 최초 준비·취소·재설치·업그레이드를 구분한다. 옵션을 켰다고 OS 저전력 모드를 변경하지 않는다. 배터리 잔량 보호를 알림 허용 여부에 종속시키지 않는다.

## 3. 미확정 항목별 추천과 이유

아래 전체는 당시의 미채택 제안이다. D-01~05는 보완 전 원문 항목이며 나머지는 해당 검토에서 드러난 선택이다. 이후 채택과 구현 승인은 현행 명세·위 후속 기록을 따른다.

| ID | 추천안 | 이유 |
|---|---|---|
| D-01 자연 종료 | 닫힌 분리·현재 배터리의 수동 만료는 원복 후 Sleep 한 번 요청. 현재 AC의 조건 해제·만료·작업 종료는 자체 해제 후 macOS에 맡김 | 원래 문제인 닫힌 분리와 배터리 소모를 우선한다. AC 작업 하나의 종료가 다른 OS 작업을 강제로 잠재우지 않게 한다. `macOS에 맡김`은 깨어 있음 보장이 아니며, 종료 시 현재 전원으로 분류한다 |
| D-02 AC 잔량 감소 | 우선 안내만, 자동 종료 없음 | 충전 여부와 AC 공급은 다르다. 지속 시간·감소량의 검증 없이 자동 종료하면 정상 작업을 잘못 끝낼 수 있다 |

| D-05 종료 알림 | 시간 만료와 명시적 연동 작업 종료를 선택 제공, 기본 OFF. 기존 ‘우선 만료만’에서 추천 변경 | 긴 빌드/명령 종료는 실제 도움이 있다. 관측한 결과만 알리고 자동 조건 변화·직접 종료 알림은 늘리지 않는다 |
| 추가-01 프리셋 구조 | 한 번에 자동 프리셋 하나 적용, 그 안에서 AND/OR | 여러 활성 프리셋·전역 설정·수동 요청의 중복 우선순위를 줄인다 |

| 추가-03 시간·연장 값 | 5/10/15/30/60/120분, 연장 +15/+30분. 배터리 시작은 최초 시작+120분까지만 | 짧은 확인과 긴 작업을 고정 선택으로 다루며 직접 입력 UI를 복원하지 않는다 |

| 추가-05 새 설치 기본값 | 준비 전 실행 없음, 자동/덮개 OFF. 준비 후 명시적으로 활성화 | 설치·인증 완료를 작업 시작 의사로 해석하지 않는다. 기존 사용자 설정은 보존한다 |

당시에는 다운로드 감지 제공자·활동 평균/유예 값·이벤트 만료·관측 실패의 재시도 한도·원복 제한 시간의 구체값이 없었다. 전원 분리/보호를 지연하지 않는 공통 계약은 유지하고, 실제 입력을 검증한 뒤 기능별 실행 명세에 **값·기준 시계·오류 결과**를 함께 정하도록 제안했다. 구체값이 정해지기 전에는 해당 확장 기능의 명세가 완성됐다고 표시하지 않는다는 당시 검토 기준이며, 후속 기준안과 남은 인수는 현행 v4 §12를 따른다.

## 4. 재검토에서 결함으로 세지 않은 항목

- 배터리 시작 수동이 AC로 이동해도 최초 시작+120분 상한을 유지한다. 명시적 연장과 자동 연장은 이미 구분돼 있다.
- 전원 분리 이전 입력의 지연 도착·재전송으로 새 배터리 수동을 만들지 않는 규칙은 이미 93행에 있다.
- OR의 다른 정상 조건을 개별 권한 오류로 막지 않는 규칙은 이미 159행에 있다. 남은 문제는 공통 필수 관측의 정확한 범위다.
- 종료 시 전원과 세션 시작 전원은 이미 128행에서 구분한다. 배터리 시작 수동의 AC 만료를 배터리 종료로 처리하면 명세 위반이다.
- 외부 스크립트가 수동 API를 호출할 수 있다는 경계는 이미 193행에 있다. 호출자가 실제 사람인지 판별하는 기능은 요구하지 않는다.
- 실제 OS Sleep 뒤 수동을 되살리지 않는 것은 이미 확정 요구다. 잠금·원격 연결만으로 수동을 끝내지는 않는다.
- 당시에는 직접 시간 입력·종료 예고·반복 유지 알림·별도 사용법 창·VoiceOver 전용 확장의 제외 결정을 다시 열지 않았다. 이후 단발 만료 예고만 사용자 요청으로 채택했으며 현행 v4 §12.10을 따른다.
- 구 실행 설계와 당시 코드의 차이는 v4가 후속 정렬 대상으로 밝힌 내용이었다. 이를 당시 v4 내부 모순으로 세지 않았다.
