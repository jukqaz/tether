# Tether 기능 명세 v4 · 앱별 강점·운영 편의 보완안

> **2026-10-20 현재 개편 계약:** 클램쉘·AC 자동 트리거·수동 절전 방지를 중심으로 제공한다. 사용자가 전역 단축키, 규칙 예행연습, 설정 이력/복원, 특정 프로세스 종료 연동 수동 유지(`run`, `manual --pid`), 작업 후 업데이트 예약의 제거를 승인했다. 이 문서와 차기 V5 시안의 해당 기능은 과거 제안이며 현행 요구를 덮어쓰지 않는다. 타이머 연장·종료/만료 예고·보호·다른 앱 충돌 진단·로그인 실행·일반 업데이트·도우미 복구는 유지한다. 앱/프로세스가 실행 중일 때의 자동 조건은 유지한다. 전원 분리 종료·배터리 최대2시간·안전 교체 정책은 변경하지 않는다. 레거시 프로세스 연동 IPC는 명시적으로 거절하고 정상 수동으로 조용히 전환하지 않는다. 구 단축키 저장값만 새 버전 정상 시작에서 정리하며 핵심 사용자 선택은 초기화하지 않는다. 설치와 물리 시험은 보류한다.

2026-10-16 갱신 · macOS 26 이상 / Apple Silicon · v4 명세·승인 시안의 구현과 자동 검증 승인. 설치·물리 시험은 보류한다. 추가 편의 옵션 요구와 구현 전 범위는 §14에서 별도로 구분한다.

**차기 설계는 [V5 기능명세](PRODUCT-SPEC-V5.ko.md)를 따른다.** 2026-10-16 사용자가 앞선 ‘핵심 규칙 유지’ 결정을 잠시 보류하고 다른 앱의 장점을 넓게 통합하도록 지시해 기본값·선택 정책·충돌·UI를 다시 정리했다. 조사 근거는 [기능 수집·통합안](../../FEATURE-SYNTHESIS-20261016.ko.md)에 남겼다. 아래 AC-only·배터리120분·분리 전체 종료 및 §14의 제외 항목은 현재 후보58의 계약·이전 결정이며 새 설계의 고정 제약이 아니다. V5는 시안 검토 단계로 앱 코드·설치본·실제 설정을 바꾸지 않았다.

**이 문서는 현재 후보58/v4의 기능·검증 기준이다.** 기존 v3 문서의 배터리 자동·전원 분리 후 승계·연장 금지와 충돌하면 이 명세를 따른다. 2026-10-15 사용자 요청에 따라 앱별 강점과 v4 검토의 보완 사항을 명세에 반영했고, 이후 사용자가 **이 명세와 승인 시안의 앱 구현·자동 검증을 승인했다.** 앞선 명세·HTML 검토 단계의 앱 미적용 제한은 당시 범위다. 명세 채택이나 구현 승인은 실행 검증 완료를 뜻하지 않는다. 현재 소스·격리 자동 회귀·UI의 근거와 남는 제한은 [v4 구현·검증 결과](../../IMPLEMENTATION-V4-20261015.ko.md)를 따른다. 설치·물리 시험은 이번 승인 범위에서 제외하며 V4-G1~G4의 전체 인수는 미완료다.

## 1. 제품 목적과 지원 대상

Tether는 **전원이 연결된 Mac의 작업을 유지하고, MacBook을 닫은 채 전원을 빼면 자신의 클램쉘 유지를 끝내는 전원 관리 앱**이다. 사용자가 배터리에서 직접 시작한 작업은 최대 2시간 유지한다. 고급 조건과 작업 연동은 이 기본 규칙 안에서 제공한다.

| 구분 | 제공 범위 |
|---|---|
| Apple Silicon MacBook / macOS 26 이상 | 일반 유지·화면 유지·자동 규칙·수동 작업·도우미 기반 선택적 덮개 유지 |
| Apple Silicon 데스크톱 Mac / macOS 26 이상 | 일반 유지·화면 유지·자동 규칙·수동 작업. 덮개/내장 배터리 기능은 해당 없음 |
| 도우미 | MacBook의 준비 절차에 필수. 실제 덮개 실행 가능 상태를 별도 확인. 데스크톱 일반 유지를 위해 설치하지 않음 |
| Intel / macOS 26 미만 | 지원 대상에서 제외 |

모델명을 하드코딩해 지원을 약속하지 않고 실제 덮개·배터리·OS 실행 기능을 확인한다. 개발 Mac의 빌드 성공을 모든 Apple Silicon 기종·macOS 26 실물 검증으로 표시하지 않는다.

### 확정한 사용자 요구

- 자동은 **AC에서만**, 배터리는 새 명시적 수동 요청으로만 시작한다.
- **모든 AC→배터리 전환은 그 전에 시작한 자동·수동·작업 연동 요청을 끝낸다.** 배터리 수동→AC→재분리도 예외가 아니다. 전원 분리 후 승계 예약은 없다.
- AC 수동은 시간제/무제한, 배터리 수동은 최대 120분이다.
- 실행 중 명시적 수동 연장과 선택적 종료 알림은 제공한다. 직접 시간 입력 UI는 제공하지 않는다.
- 2026-10-15 추가 요청으로 규칙 예행연습·작업 종료 후 업데이트·설정 변경 이력·선택적 만료 예고를 채택한다. 만료 예고의 이전 제외 결정은 §8/§12.10으로 대체한다. 그 외 직접 시간 입력·AC 자동 잠시 쉬기·복수 수동/PID는 이번 채택에 포함하지 않는다.
- 전체 일시 중지·보호·실제 OS Sleep으로 끝난 수동은 부활하지 않는다.
- 원격 앱·화면 관측이 전원 분리 규칙이나 작업 마감을 바꾸지 않는다.
- 확장 UI는 사용자가 승인한 시안을 기준으로 구현·자동 검증한다. 설치·물리 시험은 별도 단계다.

### 이번 보완에서 채택한 기본값

고정 시간은 5/10/15/30/60/120분, 실행 중 연장은 +15/+30분이다. 종료 알림·만료 예고·고급 조건·저전력 모드 종료는 기본 꺼짐으로 둔다. 작업 종료 후 설치는 대상 버전마다 사용자가 선택하며, 설정 이력은 로컬의 제한된 기록으로 제공한다. 새 설치는 실행 요청 없음·자동 OFF·덮개 유지 OFF에서 시작하고 MacBook 필수 준비를 마친 뒤 사용자가 켠다. 기존 설치의 ON/OFF·중지·보호·화면 선택은 보존한다. 로그인 시 시작·설치·인증 완료를 자동 ON이나 수동 시작 의사로 취급하지 않는다.

배터리 하한 기본값은 20%이며 열 심각/위험 중단은 끌 수 없다. 잔량 선택 범위·관측/원복 시간 제한·제공자 범위는 §12에 공식 API의 의미·참고 코드·제품 추천을 나눠 정리한다. 추천 숫자는 Apple 안전 기준이나 실측 완료 값이 아니며 적용 전 검증이 필요하다. 자연 종료 기본값은 §4.2의 원인별 동작을 따른다.

### 첫 설정: 언제 유지할지와 덮개를 닫아도 유지할지

처음 준비 안내 안에서 **AC 자동**과 **덮개 유지**를 가까이 배치하되 서로 독립인 두 선택으로 설명한다. 별도 사용법 창을 복원하거나 새 자동 모드를 만들지 않는다.

- **AC 자동:** 전원이 연결됐을 때 자동으로 작업을 유지할지 선택한다. 기본 OFF이며, 도우미 설치/인증/설정 완료만으로 켜지지 않는다.
- **덮개 유지:** 이미 유지 중인 작업을 덮개를 닫아도 계속할 수 있게 허용한다. 기본 OFF이며, 이 선택만으로 일반 유지나 수동 타이머가 시작되지 않는다.
- 첫 설정은 아직 적용하지 않은 선택·저장한 선택·현재 결과를 구분한다. 사용자가 확인해 적용하기 전에는 초안이며, AC 자동 ON 적용은 현재의 유효한 AC/보호/준비 조건에 따라 새 자동 유지를 시작할 수 있음을 짧게 안내한다. 수동 시작·전체 중지/보호 해제는 별도다.
- MacBook은 기존 필수 도우미 준비를 확인한다. 준비하지 못한 상태를 완료/실행 중으로 표시하거나 관리자 인증을 대신하지 않는다. 완료 버튼은 필요한 준비가 끝났을 때만 허용하고, 두 선택이 OFF인 채로 완료해도 작업은 시작하지 않는다.
- 데스크톱 Mac은 덮개/내장 배터리/도우미 선택을 보여주거나 설치하지 않고 AC 일반 유지 경로를 안내한다. 업데이트·재열기 때 새 설치 기본값으로 기존 설정을 덮어쓰거나 첫 설정을 다시 적용하지 않는다.

아래는 **일반 AC·보호 정상·MacBook 도우미 준비·현재 수동 없음**을 가정한 선택 결과다. ‘덮개 유지 ON’은 실행 허용이며 열린 덮개에서 이미 닫힌 상태로 실행 중이라는 뜻은 아니다.

| AC 자동 | 덮개 유지 | 적용 뒤 설명할 결과 |
|---|---|---|
| OFF | OFF | 자동 작업 대기. 새 수동 시작은 별도 |
| ON | OFF | AC에서 일반 작업 유지. 덮개를 닫아도 계속하는 기능은 사용 안 함 |
| OFF | ON | 자동 작업 대기. 이후 직접 시작한 유효 수동은 덮개 유지 사용 가능 |
| ON | ON | AC 자동 작업 유지. 덮개를 닫아도 유효한 작업을 계속하도록 허용 |

모든 조합에서 전원 분리는 기존 요청을 끝낸다. 배터리 수동 시작·최초120분·화면/잠금 정책은 기존 계약을 그대로 따른다. 예행연습·시안의 가상 조합을 실제 첫 설치 완료로 기록하지 않는다.

| F-08 | 열·배터리 보호 | 심각/위험 열 상태, 배터리 잔량 하한·저전력 경고, 필수 관측 실패에 따라 자체 유지 중단 |

| F-10 | 중지·재개·잠자기 | ‘수동만 종료’, ‘자동 OFF’, ‘모두 일시 중지’, ‘작업 재개’, ‘잠자기’를 구분 |

## 3. 전원·세션 계약

### 3.1. 자동 유지

자동 ON/OFF와 자동 모드를 구분한다.

- **AC 연결 동안:** AC가 확인되면 유지한다. 배터리 100% 또는 충전 일시 중지 상태도 AC 공급이 확인되면 같은 조건이다.
- **AC + 고급 조건:** AC와 선택한 조건 묶음이 함께 성립할 때 유지한다.
- 자동 OFF는 자동 요청만 끝낸다. 실행 중 수동의 선택·기한은 바꾸지 않는다.
- 조건이 해제돼도 다른 자동 조건 또는 수동 요청이 남아 있으면 해당 요청은 계속된다.
- 고급 모드의 빈 규칙은 시작하지 않는다. 규칙 삭제·손상·권한 실패로 ‘AC 연결 동안’ 모드로 바뀌지 않는다.
- 배터리에서는 시간표·앱/프로세스·네트워크·AI 이벤트가 자체 유지를 자동 시작하지 않는다.
- 이미 깨어 있는 MacBook은 덮개가 닫혀 있어도 AC 연결/분리를 관측해 평가한다. 잠든 Mac을 케이블 연결만으로 깨우는 것은 요구에서 제외한다.

### 3.2. 수동 유지

| 항목 | 동작 |
|---|---|
| 시간 선택 | 5·10·15·30·60·120분. 선택값 저장은 다음 시작의 기본값이며 현재 요청을 바꾸지 않음 |
| 무제한 | AC에서만 표시·시작 가능. 자동 OFF에서도 명시적 수동 시작 가능 |
| 배터리 | 새 명시적 시작만 허용, 최초 시작부터 최대120분 |
| 동시 수동 | 사용자 수동 세션은 하나. 활성 중 다른 수동/PID 시작은 ‘이미 수동 유지 중’으로 거절하고 기존 대상·마감 보존. 동일 요청 재전송은 재실행 없이 원래 처리 결과와 현재 요청 상태를 함께 반환 |
| AC 연결 | 배터리 수동의 기존 마감·최초120분 상한 보존. AC 자동이 별도로 병행할 수 있음 |
| AC 분리 | 남은 수동 시간과 시작 전원을 불문하고 기존 요청 종료 |
| 재시작/업데이트/Wake | 종료된 수동 복원 없음. 허용된 AC 자동만 다시 평가 |
| 화면 잠금/설정 창/원격 접속 | 그 사실만으로 수동을 끝내거나 시간을 늘리지 않음. 실제 OS Sleep·로그아웃·소유자 종료와 구분 |

처음 배터리에서 30분 시작한 뒤 10분 후 AC를 연결해도, 연장을 누르지 않으면 최초 시작의 30분 마감이 그대로다. AC를 다시 빼면 남은 시간이 있어도 종료한다.

분리 이후에 새로 요청한 수동 시작만 새 배터리 요청으로 인정한다. 분리 이전 시작 명령·키 입력의 지연 도착, 재전송·ACK·IPC 재접속은 새 시작이 아니며 분리 종료를 취소하지 않는다.

실제 OS Sleep이 확인되면 현재 수동·명시적 작업 요청을 소비한다. FullWake에서 만료 전 잔여 시간이 있어도 이어 실행하지 않으며, 전체 중지/보호가 없다면 현재 AC 자동만 재평가한다. 분리 자체는 새 배터리 수동까지 금지하는 전체 중지와 다르다.

새 명시적 수동/PID 시작은 요청한 유효 기능의 적용 확인 전까지 `준비 중`이다. 필요한 일반/화면/덮개 중 일부만 적용됐거나 승인이 끝내 실패하면 새 요청을 거절하고 그 요청 때문에 얻은 자원만 회수한다. 기존 다른 요청은 보존하며 미승인 감싼 명령을 실행하지 않는다. 이미 승인된 요청에서 나중에 도우미 통신만 실패한 경우의 기능별 제한은 §7을 따르며 새 시작의 부분 실패와 구분한다.

시작/연장 응답이 미확인이면 같은 요청 ID의 현재 결과를 먼저 조회한다. 자동으로 새 ID를 만들어 재시작하지 않는다. 이미 끝난 요청의 옛 ‘승인’ 결과를 현재 활성 상태로 표시하지 않으며, 남은 요청 ID/종료 원인과 함께 설명한다. 만료한 대기 명령이 뒤늦게 도착해도 새 승인으로 재생하지 않는다.

### 3.3. 실행 중 연장

- 시간제 수동이 활성인 동안 +15분/+30분으로 현재 마감을 연장한다. 무제한에는 연장 조작을 표시하지 않는다.
- ‘연장’은 기존 마감에 더하는 동작이다. 지금부터 새 시간으로 마감을 교체하거나 세션을 재시작하는 `Stop in` 동작은 제공하지 않는다.
- 배터리 시작 요청은 AC로 이동해도 **최초 시작+120분**을 넘지 않는다. 선택한 +15/+30분 전체를 추가할 수 있을 때만 해당 버튼을 활성화한다. 상한에 맞춰 일부 분량만 더하거나 숨은 직접 입력으로 바꾸지 않는다. 예를 들어 상한까지7분이면 두 버튼 모두 비활성이다.
- 전원 연결·프리셋·관측 갱신·heartbeat는 연장 의사가 아니다. 사용자의 명시적 연장만 마감을 바꾼다.
- 분리·만료·전체 중지·보호·OS Sleep이 먼저 관측돼 끝난 요청은 연장할 수 없다. 새로 시작하려면 별도 명시적 시작이 필요하다.
- 승인 전·거절·일반/덮개 적용 실패를 연장 완료로 표시하지 않는다. 구버전 도우미가 연장을 지원하지 못하면 기존 마감을 유지한다.
- 필요한 실행기 중 일부만 확인한 상태는 연장 완료가 아니다. 승인 대기 중 기존 마감은 유효하며, 만료/분리/보호가 먼저 확정되면 대기 연장을 취소하고 부분 적용도 회수한다. 일반 요청과 도우미의 실제 기한이 다른 실패를 기록하며 기존 기한을 넘는 허가를 방치하지 않는다.
- 연장 승인 뒤 이전 마감의 종료 콜백·알림·늦은 ACK가 작업을 조기 종료하거나 마감을 되돌리지 못해야 한다.

### 3.4. 요청이 겹칠 때

| 사건 | 자동 | 수동/명시적 작업 |
|---|---|---|
| 수동만 종료·수동 만료 | 조건이 유효하면 계속 | 해당 요청 종료 |
| 자동 OFF·마지막 자동 조건 해제 | 자동 종료 | 기존 마감까지 계속 |
| AC→배터리 | 기존 요청 모두 종료 | 기존 요청 모두 종료 |
| 모두 일시 중지 | 재개 전까지 시작 금지 | 종료, 복원 없음 |
| 보호 중지 | 원인 해소+명시적 재개 전까지 시작 금지 | 종료, 복원 없음 |
| 작업 재개 | 중지를 해제한 뒤 AC 조건 재평가 | 새로 시작하지 않음 |
| 원격 연결·가상 화면 변화 | 설정한 독립 조건이 없다면 수명 변화 없음 | 수명·마감 변화 없음 |
| 실제 OS Sleep | 현재 요청 정리. FullWake에서 허용된 AC 자동만 재평가 | 모두 소비, 잔여 시간 복원 없음 |

사용자 ‘모두 일시 중지’와 보호 중지는 FullWake만으로 해제하지 않는다. Tether의 명시적 ‘잠자기’가 만든 별도 중지는 §4.2대로 해당 요청 이후의 실제 Sleep→FullWake 또는 명시적 재개로만 해제한다. Sleep 명령 성공·AC 재연결·원격 접속은 해제 근거가 아니다.

자동 OFF→ON·프리셋 적용·가져오기·재로그인으로 전체 중지/보호를 암묵 해제하지 않는다. 보호 원인이 남아 있으면 재개도 거절한다. 새로운 시작과 중지 해제는 서로 다른 의사다.

일반 유지와 별개로 화면/덮개의 전역 허용 범위를 둔다. **실제 실행은 유효한 Tether 요청 중 하나 이상이 요구하고 전역 허용·해당 기능의 준비/보호 조건이 모두 맞을 때만** 켠다. 전역 ON만으로 새 일반 작업을 만들지 않는다. 한 요청의 OFF·유휴 후 화면 해제는 다른 요청의 요구를 취소하지 않는다. 전역 OFF·보호는 모든 요청보다 우선해 해당 기능을 해제하지만, 기능별 OFF만으로 일반 유지·현재 수동 마감을 바꾸지 않는다. 원래 요청의 선택값과 실행 결과는 구분한다.

## 4. 종료 동작과 우선순위

### 4.1. 공통 처리

‘유지 종료’, ‘자체 원복 확인’, ‘잠자기 요청’, ‘실제 OS Sleep’은 다른 상태다. 끝난 요청의 새 획득을 막고 자신의 자원을 정리한다. 선택된 잠자기 동작은 원복과 최신 전원·덮개·현재 요청 확인 뒤 한 번 요청한다. 원복 실패를 성공으로 표시하지 않으며 타사 전역값을 강제로 0으로 만들지 않는다.

종료 알림을 띄우려고 원복·잠자기를 지연하지 않는다. 닫혔다는 과거 관측만으로 열린 Mac을 뒤늦게 잠재우지 않는다. 분리/자연 종료에 따른 미실행 Sleep은 AC 재연결·새 유효 요청·소유자 변경·종료 동작 권한 만료로 무효화할 수 있다. 종료 원인인 수동 마감과 종료 동작 권한의 마감을 혼동하지 않는다. 명시적 ‘잠자기’의 중지 해제는 §3.4/§4.2를 따르며 전원 변화만으로 재개하지 않는다.

### 4.2. 종료 원인별 기본값

2026-10-15 사용자는 ‘원인별 처리’를 선택했다. 닫힌 상태의 마지막 유지 종료에서 **전원 분리·배터리 수동 만료는 잠자기 요청, AC 조건 해제·AC 작업 완료는 macOS에 맡김**을 기본으로 확정했다. 아래의 연동 작업·직접 종료·보호 등 세부 계약은 해당 원인과 현재 전원을 구분한다.

원인별 기본값을 아래처럼 명세에 반영한다. `macOS에 맡김`도 Tether 자체 유지는 반드시 해제하며, Mac이 계속 깨어 있다는 보장은 아니다. 다른 요청 예외는 **종료 사건 이후에도 유효한 Tether 요청**에만 적용한다. 분리 이전의 요청은 이 예외로 살아남지 않는다.

아래 표의 AC/배터리는 **종료를 판단하는 현재 전원**이다. 배터리에서 시작한 수동이 AC에서 만료하면 AC 행을 따르며, 최초 시작+120분 상한과 종료 시 동작을 구분한다.

| 원인·현재 상태 | 유지 종료 | 잠자기 기본값 |
|---|---|---|
| AC 분리·덮개 열림 | 모든 기존 요청 종료 | 강제 Sleep 없음 |
| AC 분리·덮개 닫힘 | 모든 기존 요청 종료 | 원복 확인 뒤 Sleep 한 번 요청. 사용자가 ‘macOS에 맡김’을 고를 수 있음 |
| 배터리 수동 시간 만료/연동 작업 종료·덮개 닫힘·다른 유효 Tether 요청 없음 | 해당 수동 종료 | 원복 확인 뒤 Sleep 한 번 요청 |
| AC의 자동 조건 해제·수동 만료·작업 종료·덮개 닫힘·다른 유효 Tether 요청 없음 | 끝난 요청 정리 | 자체 원복 후 macOS에 맡김 |
| 유효한 다른 Tether 요청이 남은 자연 종료 | 끝난 요청만 종료 | 전체 Mac Sleep 요청 없음. 분리·보호·전체 중지의 기존 요청 소비를 취소하지 않음 |
| 사용자가 ‘수동만 종료’·자동 OFF 선택 | 선택한 출처만 종료, 다른 유효 Tether 요청 보존 | 자체 해제 후 macOS에 맡김. ‘잠자기’ 명령과 구분 |
| 심각/위험 열 보호·배터리 보호 | 자체 요청 중단 | 닫혔고 현재 보호·소유·원복 확인을 통과하면 보호 Sleep 한 번. 센서 미확인만으로 Sleep 성공을 추정하지 않음 |
| 사용자가 Tether의 ‘잠자기’ 선택 | 기존 요청 종료·자동 일시 중지 | 원복 후 한 번 요청. 실제 Sleep→FullWake 확인 전 또는 실패 시 중지 유지 |

어떤 정책도 잠자기 요청 성공만으로 실제 잠자기를 보장하지 않는다. 타사 유휴 assertion과 시스템 전체의 전역 차단을 구분해 실패·미확인을 설명한다.

타사 유휴/화면 assertion의 존재만으로 선택된 닫힌 분리 Sleep 요청을 생략하지 않는다. 미소유 전역 `SleepDisabled` 차단은 강제 해제하거나 Tether 소유로 채택하지 않는다. 실행 전 확인에서 전역 차단·소유권/자체 원복 미확인으로 요청할 수 없으면 그 제한을 기록하며, Sleep을 시도했거나 성공했다고 표시하지 않는다. 두 경우를 같은 ‘다른 앱 때문에 대기’로 합치지 않는다.

열린 상태의 자연 종료는 화면/덮개 선택과 무관하게 자체 해제 후 macOS에 맡긴다. 배터리 연동 작업의 정상/오류 종료도 유지 요청의 종료이며, 닫혔고 다른 유효 Tether 요청이 없으면 위 배터리 행을 따른다. 관측 실패를 작업 완료로 바꾸지 않고 §7의 제한/보호 규칙을 적용한다.

### 4.3. 우선순위

1. 실제 소유자 종료·로그아웃·OS Sleep, 보호 조건, 사용자 전체 중지.
2. 확인된 AC 분리로 기존 요청 전체 소비, 완료·만료된 요청 종료.
3. 안전 조건을 만족하는 새 명시적 수동 의사.
4. 허용된 AC 자동 조건.

종료와 연장이 경합하면 먼저 관측돼 확정된 종료를 연장으로 되돌리지 않는다. 전원/센서 미확인을 정상 또는 새 AC 전환으로 대체하지 않는다. 센서 실패와 분리가 겹쳐도 두 사실을 따로 기록하며 원래 분리 사건을 보호 이유로 덮어 잃지 않도록 한다.

마지막으로 확인한 전원과 현재 관측의 유효성을 분리한다. `AC→미확인→배터리`는 기존 요청의 분리를 한 번 소비하고, `AC→미확인→AC`는 가짜 분리·새 연결을 만들지 않는다. 보호로 먼저 끝난 경우에도 이후 확인한 실제 전원 전이를 기록한다. 미확인 상태에서 받은 입력은 나중에 정상 값이 왔다는 이유로 새 수동 승인으로 재생하지 않는다.

수동 마감·표본 유효기간·이벤트 TTL·허가/종료 권한은 수신 측 수면 포함 연속 시계로 계산한다. 벽시계·시간대·DST는 시간표와 일정의 현재 구간 평가에만 사용한다. 부팅을 넘겨 연속 시계 값을 실행 권한으로 복원하지 않는다. 실제 Sleep·소유자 종료/변경·교체는 대기 시작/연장을 취소하며, Sleep 통지 응답을 IPC·원복 재시도 완료까지 붙잡지 않는다. 공식 근거와 시간 추천은 §12.2~3에 둔다.

### 4.4. 앱·업데이트·소유자의 수명

- 정상 종료는 자체 요청 종료·원복을 수행한다. 비정상 종료는 기존 허가의 유한 만료와 감시 장치로 회수하고 원복 미확인을 남긴다. 연결이 끊겼다는 이유만으로 원복 완료를 표시하지 않는다.
- 작업 종료 후 설치 예약/취소는 현재 요청을 끝내지 않는다. 예약 대기 대상과 안전한 교체 경계는 §12.8을 따른다.
- 업데이트 확인·다운로드·실제 앱 종료 전의 취소만으로 정상 수동을 끝내지 않는다. 실제 종료/교체 단계에 들어가면 수동/명시적 작업 요청을 소비한다. 새 프로세스는 원본·미완료 원복·호환성을 확인한 뒤 허용된 AC 자동만 평가하며 옛 수동·명령을 재생하지 않는다.
- 동시에 여러 앱 프로세스/CLI/위젯이 전원 실행의 소유자가 되지 않는다. 일반 CLI/확장은 공통 명령 접점으로 요청하며 독립 assertion으로 정책을 우회하지 않는다.
- 빠른 사용자 전환은 활성 소유자 변경으로 취급해 이전 사용자의 권한을 정리한다. A→B→A에서 A의 수동은 부활하지 않는다. 단순 잠금·원격 연결·DarkWake는 새 사용자 의사나 FullWake로 취급하지 않는다.
- 소유자가 끝난 뒤 허용할 동작은 검증된 자체 원복이다. 이전 소유자의 대기 중 Sleep·새 획득·연장을 뒤늦게 실행하지 않는다. 실제 Sleep 이후 자동 재평가는 FullWake·현재 소유·전원·보호를 새로 확인한 뒤 수행한다.

## 5. AC 자동 규칙과 프리셋

### 5.1. 조건 조합

조건 묶음 안은 ‘모두 만족(AND)’, 묶음 사이는 ‘하나 이상 만족(OR)’이다. **AC·전체 중지·보호·현재 소유자 확인은 조합 밖의 필수 조건**이다.

평가에서는 `충족 / 불충족 / 미확인 / 권한 필요 / 지원 안 됨`을 구분하되 모든 내부 상태를 화면에 나열하지 않는다. 사용자가 고른 조건의 결과와 필요한 조치만 §9대로 표시한다. 필요한 관측이 미확인이면 실행 권한을 만들지 않는다. 평균·유예가 있는 부하 조건도 전원 분리·사용자 중지·보호를 지연하지 않는다.

미확인은 해당 조건/묶음에 적용한다. AND 묶음은 필요한 조건이 모두 확인돼 충족될 때만 유효하고, OR에 정상적으로 충족된 다른 묶음이 있으면 그 묶음은 독립적으로 유효하다. 개별 기기·일정 권한 실패 때문에 정상인 다른 묶음이나 수동 작업을 전체 차단하지 않는다. 전원·보호·소유자 같은 공통 필수 조건의 미확인은 별도다.

| 조건군 | 선택할 대상 | 표시·오탐 경계 |
|---|---|---|
| 앱·프로세스 | 실행 중/최전면 앱, 특정 프로세스 | 실행 중과 실제 작업 중을 구분. PID 재사용·조회 실패 처리 |
| 시간표 | 요일·시작/종료 시간·자정 넘김 | 시간대·DST·수면 복귀에 현재 구간만 평가. 놓친 시작을 소급하지 않음 |
| 네트워크 | 선택한 Wi-Fi·VPN·IP/DNS | 읽기 전용. 권한 거부/관측 실패를 불충족과 구분 |
| 기기·환경 | USB/Bluetooth·볼륨·오디오 출력·화면 | 실제 대상 identity와 연결/마운트 상태. 물리/가상 화면 구분 |
| 활동 | CPU·전송량·다운로드 진행 | 낮은 부하·잠깐의 무변화를 작업 완료로 단정하지 않음 |
| 일정·회의·미디어 | 선택한 일정과 지원이 확인된 제공자 | 앱 실행만으로 통화/재생 중이라고 표시하지 않음. 제공자 목록은 검증 후 확정 |
| 작업 이벤트 | 사용자가 연결한 AI·빌드 작업 | 시작/대기/완료·수명 만료를 구분. 프롬프트/채팅 내용 수집 없음 |

### 5.2. 프리셋

AC 기본·개발/빌드·회의·원격 작업 등 이름 있는 조건 설정을 제공하고 저장·복제·이름 변경·삭제를 지원한다. 프리셋은 실행 중인 요청이나 권한을 저장하는 파일이 아니다.

자동 프리셋은 **한 번에 하나만 적용**한다. 프리셋 안의 여러 조건 묶음은 AND/OR로 조합하며 저장된 여러 프리셋을 각각 독립 실행기로 만들지 않는다. 적용된 프리셋/저장된 사본/현재 실행 중 요청을 구분한다.

적용한 자동 규칙은 즉시 재평가하되 실행 중 수동의 시간·화면·덮개 선택은 보존한다. 프리셋의 수동 기본값은 다음 시작부터 사용한다. 다른 유효한 요청이 화면/덮개를 요구하면 한 요청의 OFF만으로 그 요청까지 해제하지 않는다. 전역 허용 OFF·보호는 §3.4대로 실제 실행에 우선한다.

고급 규칙을 처음 켜거나 프리셋을 가져올 때 활성 조건·권한 누락·즉시 시작 가능성을 보여준다. 단순 선택/미리보기만으로 자동 ON 또는 수동 시작을 수행하지 않는다.

적용 중 프리셋을 삭제하면 자동 규칙의 유효 근거가 없어졌음을 표시하고 해당 자동 요구를 끝낸다. 다른 프리셋·‘AC 연결 동안’ 모드를 자동 선택하지 않으며 수동의 대상·기한은 보존한다. 사용자가 새 모드/프리셋을 명시적으로 적용하기 전까지 고급 빈 규칙은 시작하지 않는다.

앱·프로세스는 실행/최전면/관측 미확인을, 일정은 사용자가 고른 캘린더·대상 구간을 설명한다. 회의·미디어는 검증된 제공자와 관측 상태만 지원한다. CPU/전송량·다운로드·장치 점유를 실제 작업 성공·실제 회의·사람의 참석으로 확대하지 않는다. 목록과 관측 임계값이 미확정인 제공자는 지원 완료로 노출하지 않는다.

## 6. 작업 연동과 외부 조작

### 6.1. 작업 수명

- **다운로드 자동 관측 / AI·빌드 이벤트:** AC 자동의 입력이다. 전원 분리 시 소비하고 배터리에서 진행 신호가 계속 와도 재시작하지 않는다.
- **명시적 명령/PID 연동 수동:** 사용자가 시작한 작업의 종료와 수동 마감을 연결한다. 작업 종료·상한·보호·전원 분리 중 먼저 오는 사건에서 유지가 끝난다. 작업 프로세스를 임의 종료하지 않는다.
- 새 수동/PID 작업은 기존 수동이 있으면 거절한다. 기존 ID·기한·연결 대상을 유지하며 교체·합치기는 제공하지 않는다. 유지가 승인되지 않은 새 감싼 명령은 실행하지 않고 오류를 반환한다. 이미 실행 중인 외부 PID에는 영향을 주지 않는다. 동시에 여러 작업을 관측하려면 AC 자동 조건 묶음을 사용한다.
- 이벤트 heartbeat는 관측 생존을 확인할 뿐 배터리120분·사용자 마감·소비된 요청을 연장하지 않는다.
- AC 재연결에서는 현재의 앱/시간표 등 조건을 새로 평가할 수 있지만 소비된 작업 이벤트·lease를 재생하지 않는다. 동일 작업의 늦은 시작/종료/heartbeat는 새 작업 시작이 아니다.
- 자동 관측의 무변화·공백은 완료 증거가 아니다. 확인된 완료·실패·사용자 취소·기한 만료를 구분한다.
- 직접 실행한 명령의 관측 가능한 종료 코드와 외부 PID의 소멸을 구분한다. PID 재사용을 같은 작업으로 보지 않으며, 외부 PID 종료는 ‘프로세스 종료’이고 성공/실패 증거가 아니다. 작업 취소/유지 종료가 작업 프로세스 강제 종료를 뜻하지 않는다.
- AI·빌드 연동은 `작업 중 / 사용자 응답 대기 / 유휴 / 종료 / 관측 만료`와 근거 출처를 구분한다. 도구가 직접 보낸 상태와 활동량에 따른 추정을 같은 확실성으로 표시하지 않는다. 응답 대기는 유효한 작업 이벤트의 기한 안에서만 유지 사유가 될 수 있으며 무기한 heartbeat 우회가 아니다. 프롬프트·채팅·전체 작업 인수는 읽거나 저장하지 않는다.

### 6.2. 조작 진입점

메뉴·전역 단축키·Shortcuts/App Intents·CLI/URL·위젯/제어 센터는 같은 시작·종료·중지·상태 확인 의미를 사용한다. 단축키는 기본 미지정으로 두고 등록 충돌을 설명한다. 위젯/외부 명령에 더 강한 전원 권한을 주지 않는다.

각 접점은 `승인 / 이미 처리됨 / 거절 / 제한·지원 안 됨 / 처리 미확인`을 구분하고 요청 대상·이유를 반환한다. 명령 전달 성공을 실제 일반/화면/덮개 적용 또는 Sleep 성공으로 표시하지 않는다. 전역 단축키 교체 등록이 실패하면 기존 유효 키를 보존한다. UI의 빠른 조작도 ‘수동 시작/수동만 종료/모두 중지/자동 ON·OFF’의 범위를 숨기지 않는다.

‘명시적’은 **수동 시작 명령을 요청했다는 뜻**이며 호출자가 사람인지 프로그램인지 자동 판별한다는 뜻은 아니다. 사용자가 외부 스크립트/단축어로 수동 API를 호출하는 경우 출처를 표시하고 동일한 배터리 상한·분리 종료를 적용한다. Tether 자체 시간표·자동 조건은 수동 API로 바꿔 배터리 규칙을 우회하지 않는다. 따라서 ‘배터리 자동 없음’은 Tether의 자동 규칙 계약이며 모든 외부 자동화를 차단하는 보안 기능은 아니다.

## 7. 화면·잠금·원격·보호

### 화면과 잠금

일반 유지와 화면 유지는 독립이다. 기본은 macOS 화면 절전 허용이며 ‘작업 중 화면 유지’를 선택하면 유효한 요청 동안 화면 유휴 절전을 억제한다. 유휴 후 화면 유지 해제 옵션은 해당 요청의 화면 요구만 끝내고 일반 작업은 유지한다.

**목표:** 작업 중 원치 않는 잠금을 줄이고 닫힌 원격 작업을 안정적으로 유지한다. **지원 경계:** Tether의 작업/화면 유지가 자동 잠금 해제나 OS 암호 정책 변경은 아니다. 실제 화면 꺼짐·패널 소비 전력0·무잠금·원격 프레임/입력은 서로 다른 결과다. 현재 자료만으로 ‘화면을 실제 끄면서 모든 환경에서 무잠금’을 확정 기능으로 약속하지 않는다.

원격 앱이 실행 중이라는 이유로 기본 메뉴바 아이콘 폭·수동 마감·전원 분리 동작을 바꾸지 않는다. 사용자가 원격 앱을 고급 조건으로 명시적으로 추가한 경우 그 조건의 관측만 사용한다. 원격 앱을 직접 종료하지 않는다.

### 보호

OS 열 상태가 심각/위험이면 전원·자동/수동과 무관하게 자체 유지를 중단한다. 열 보호 OFF, 임의 섭씨 임계값, 팬 강제는 제공하지 않는다. 배터리 수동에는 사용자 잔량 하한(기본20%)·OS 저배터리 경고도 적용한다. 잔량이 하한 이하이면 시작을 거절하고 실행 중이면 종료한다. 시작 경고를 무시해 보호를 우회하는 선택은 제공하지 않는다.

저전력 모드 종료는 기본 OFF인 배터리 수동의 선택 조건이다. ON이면 시작 때 이미 저전력 모드인 경우도 거절하고 실행 중 진입하면 종료한다. 모드가 풀려도 수동을 부활시키지 않는다. AC에 있던 저전력 모드만으로 AC 작업을 종료하지 않으며, 옵션이 OS 전원 모드를 변경하지 않는다.

### 관측 실패와 기기별 적용 범위

관측은 `유효한 확인값 / 미확인·만료 / 해당 없음`을 구분한다. 마지막 확인값은 사건의 전후 관계를 복원하는 근거이며 유효기간이 지난 실행 허가를 대신하지 않는다. 단일 조회 실패와 아직 유효한 이전 표본, 필수 관측 자체의 만료를 같은 상태로 처리하지 않는다. 유효기간은 §12에서 확정할 실행 설계 값이다.

| 관측 범위 | 실패·만료 때의 처리 | 회복 때의 처리 |
|---|---|---|
| 공통 전원·OS 열 상태·활성 소유자 | 유효한 공통 사실이 없으면 새 시작·연장·허가 갱신을 승인하지 않고 자체 요청을 보호 중지·원복. 미확인만으로 Sleep 권한이나 실제 Sleep 성공을 만들지 않음 | 원인 해소+명시적 재개 필요. 끝난 수동은 다시 시작해야 함 |
| 현재 배터리 수동의 잔량·OS 저배터리 상태, 종료 옵션 ON일 때의 저전력 모드 | 필요한 보호 관측이 미확인/만료이면 시작·연장·갱신 금지·해당 수동 보호 종료·원복. 유효한 이전 표본이 남은 단일 조회 실패와 구분. 정상 AC·내장 배터리 없는 데스크톱에 이 요건을 확대하지 않음 | 관측 회복 뒤 명시적 재개 필요. 기존 수동은 부활하지 않고 새로 시작해야 함. LPM 종료 OFF이면 LPM 조회 실패만으로 차단하지 않음 |
| MacBook 도우미 준비/호환·덮개/실행 관측 | 해당 덮개 허가의 새 획득/갱신 중단, 기존 허가 유한 회수. 일반/화면은 공통 사실과 원래 요청/기한이 유효하고 전체 보호 중지가 없을 때만 보존 | 아직 살아 있는 요청만 최신 전원·소유·덮개·도우미를 새로 확인해 적용 가능. 소비/만료/보호 종료한 요청은 재접속으로 부활하지 않음 |
| 선택한 앱·일정·네트워크·기기 등 개별 조건 | 해당 조건/AND 묶음을 미확인으로 처리. 무관한 정상 OR 묶음·수동은 보존 | 현재 조건만 재평가. 배터리 자동·과거 작업 이벤트 재생 없음 |
| 데스크톱의 덮개·내장 배터리 | 기능 자체가 `해당 없음`. 부재를 관측 실패로 처리하거나 도우미 설치를 요구하지 않음 | 일반/화면·AC 자동은 지원되는 공통 관측으로 평가 |

도우미 `미설치 / 승인 필요 / 호환 안 됨 / 연결 미확인 / 실제 실행 미확인 / 원복 대기·실패`는 내부 판단에서 구분한다. UI에는 확인된 결과와 현재 가능한 ‘준비하기/다시 확인/업데이트’ 조치만 설명하며, 확인할 수 없는 장애 원인을 추정해 별도 화면을 만들지 않는다. MacBook 필수 준비를 임의로 완료 처리하지 않는다. 통신 시간 초과는 도우미 사망·원복 성공의 증거가 아니다. 앱은 도우미 응답을 기다리느라 확인된 전원 분리·마감·보호의 요청 소비를 미루지 않는다. 확인된 자체 원복 실패 등 전체 보호 중지에 해당하는 사건은 일반/화면 보존의 예외이며 종료 후 명시적 재개를 요구한다.

전원 API 반환만으로 하위 경로의 모든 실패를 검출했다고 주장하지 않는다. 최신 snapshot·전원 목록/설명·종류/상태/잔량의 유효성과 aggregate 결과를 교차 확인하며 모순은 미확인으로 둔다. 알려진 MacBook의 내장 배터리 누락과 정상 데스크톱의 빈 내장 배터리 목록을 구분한다. 공개 Apple 구현의 경고 `None`/출처 `AC` fallback은 §12.6의 관측 한계이며 설치된 OS의 실패를 재현했다는 뜻이 아니다.

AC 연결·원격 연결·업데이트는 보호 중지를 해제하지 않는다. 보호 기준이 충족돼 끝낸 수동을 잔량/열 상태 회복만으로 자동 재획득하지 않는다. 센서 미확인·도우미 장애·기능 미지원의 표시를 합치지 않는다.

UPS·외부 전원 출처 미확인은 정상 AC로 대체하지 않는다. 전원은 `정상 외부 공급 / 내장 배터리 / UPS 백업 / 미확인`으로 구분한다. UPS 장치 연결만으로 백업 공급이라고 보지 않는다. `AC→UPS 백업`·`AC→미확인→UPS 백업`에서도 기존 AC 요청을 소비하고 자체 원복한다. 첫 v4의 UPS 백업 새 자동·무제한·수동 유지는 보류하고 이유를 표시한다. 정상 외부 공급 복귀는 끝난 수동을 되살리지 않는다. 이 제한을 내장 배터리가 없는 정상 AC 데스크톱 전체에 적용하지 않는다. 실제 분류 가능한 UPS 장치 범위는 별도 인수 대상이다.

AC 공급인데 잔량이 줄어드는 상황은 안내만 제공하며 자동 종료는 이번 범위에 넣지 않는다. 안내의 지속 시간·감소량 기준은 관측으로 확정한다. 충전 중 아님·100% 충전 중지 상태만으로 배터리 공급/충전 부족이라고 단정하지 않는다.

## 8. 알림·상태·설정

### 알림

- **만료 예고:** 기본 꺼짐, 수동 유지 기한 5분 전 요청당 최대 한 번. 종료 알림과 독립이며 연장/옛 알림 액션/짧은 시간의 처리는 §12.10을 따른다.
- **종료 알림:** 기본 꺼짐. `수동 시간 만료 / 명시적으로 연결한 작업 종료`를 선택 제공하고 사용자가 켤 때 OS 권한을 요청한다. 기존 과열/관측 실패·배터리 보호 알림 선택과 독립적으로 저장한다.
- AC 자동이나 다른 유지 이유가 남으면 “수동 시간 종료 · 자동/다른 작업 유지 중”으로 설명한다. 알림을 실제 Sleep 확인으로 표시하지 않는다.
- 직접 종료는 조용히 처리한다. 보호 알림과 중복하지 않고, 연장 뒤 이전 마감 알림을 취소한다. 오래된 사건이 Wake 뒤 몰리지 않게 한다.
- 직접 실행해 확인한 종료 코드만 정상/실패의 근거로 사용한다. 외부 PID 소멸은 ‘연결한 프로세스 종료’로 알리고 성공으로 바꾸지 않는다. 관측 실패는 완료 알림이 아니며 상태/제한으로 설명한다.
- 만료 예고 외의 반복 ‘유지 중’·자동 조건 변화마다의 알림은 제공하지 않는다. OS 알림 거부·집중 모드에도 보호·원복·잠자기 동작은 독립적으로 수행한다. 권한을 나중에 켜도 지난 알림을 재생하지 않는다.

### 상태·진단

설정 ON/OFF, 현재 요청, 실제 일반/화면/덮개 실행, 보호·제한, 원복 실패, Sleep 요청과 실제 Sleep을 구분한다. ‘켜짐’ 한 단어로 합치지 않는다.

기본 화면은 현재 확인한 유지 이유·남은 시간·가능한 조작만 보여준다. 사용자가 연 조건 상세에는 확인 가능한 출처·대상·조건 결과를 제공하되, 확인할 수 없는 항목을 추정하거나 빈 항목으로 채우지 않는다. 유효 기한·마지막 관측 시각·요청 식별자 등 내부 근거는 필요한 진단에서만 조회한다. 최근 결정에는 확인한 사건·시작/거절/종료 결과와 자체 원복/실행 결과를 제한적으로 연결해 재실행 뒤에도 조회할 수 있게 한다. 수치가 확인되지 않은 전력 절감량·효율 점수는 만들지 않는다.

다른 앱 영향 상세에는 실제 확인한 앱/시스템 이름·요청 종류·확인할 위치만 제공한다. 관측 시각은 필요할 때 상세에 표시하며 귀속·영향 범위를 알 수 없으면 이를 추정해 표시하지 않는다. 단순 요청 존재를 이번 실패의 원인으로 단정하지 않는다. 자체 유지가 꺼져도 타사 요청이 남아 있음이 확인되면 그 사실만 설명한다. 알 수 없는 원인을 찾기 위한 별도 상시 감시·추가 권한 요청은 만들지 않는다.

기본 기록은 로컬의 제한된 상태·이유 기록이다. 사용자가 켠 상세 기록은 기간·보관 위치·종료 조작을 보여준다. 불필요한 스크린샷·채팅·프롬프트·전체 프로세스 인수를 수집하지 않는다. 바탕화면에 자동으로 파일을 만들지 않고 사용자 내보내기는 저장 위치를 선택한다.

조회 실패·빈 내보내기·표본 공백을 사건 없음이나 실제 Sleep으로 바꾸지 않는다. 보고서는 조회 성공 여부·요청한 범위·실제 포함한 범위·누락을 표시한다. 내보내기 72시간 선택은 72시간 로그 보관을 보장하지 않는다. 회전/저장 실패를 기록 삭제로 숨기지 않고 상세 기록을 제한하며, 미완료 자체 원복 저널은 일반 로그 정리와 별도로 보존한다.

### 설정 전송·업데이트

설정·규칙·프리셋만 전송한다. 활성 요청·PID·실행 권한·토큰·원복 저널은 가져오지 않는다. 새 기능은 비활성 상태로 검토하고 실행 중 수동은 변경하지 않는다.

가져오기는 적용 전 차이·누락 권한·미지원 조건을 먼저 표시한다. 기본은 같은 이름도 구분한 **비활성 복사본 추가**이며 기존 프리셋을 덮어쓰지 않는다. 전역 옵션 교체는 항목별 명시 적용으로 나누고, 현재 수동/전체 중지/보호/활성 권한은 가져오기로 바꾸지 않는다. 현재 수동을 바꿀 전역 변경은 적용을 보류하고 이유를 설명한다. 미리보기·취소·손상·미지원 버전은 부분 적용 없이 종료한다. 알 수 없는 AND 조건을 버려 규칙을 약화시키거나 단순 AC 모드로 바꾸지 않는다.

이전 AC 자동·꺼짐·보호·잔량/화면 선택을 보존한다. 배터리 전용 자동을 AC 자동 ON으로 임의 변환하지 않는다. 퇴역한 배터리 자동·승계 설정을 새 실행 권한으로 쓰지 않는다. 원복 원본과 실패 기록은 변환·업데이트·제거 중에도 확인 없이 지우지 않는다.

설정 변경 이력/되돌리기는 설정 가져오기와 구분하며 §12.9를 따른다. 이전 설정을 복사하는 기능이 현재 수동·보호·OS 권한이나 실행 권한 복원이 되지 않는다. 작업 후 설치의 대상/대기/취소와 실제 교체는 §12.8을 따른다.

### 앱 기본 설정 보존

- 로그인 시 시작은 앱 실행 여부만 바꾸며 자동 ON·수동 시작·보호 해제를 대신하지 않는다.
- 언어는 macOS와 같게/한국어/영어를 제공한다. 언어·날짜 표시 변경은 현재 요청·마감·조건 의미를 바꾸지 않는다.
- 업데이트 자동 확인·수동 확인과 정식/정식+베타 채널을 제공한다. 채널 변경만으로 현재 버전을 강등 설치하지 않는다. 실제 교체 수명은 §4.4를 따른다.

## 9. UI와 사용성 요구

기본 화면은 메뉴·작업 유지·기기 보호·앱 설정 네 개, 설정 탐색은 기존3개 탭을 기준으로 한다. **그래파이트 + 블루·컴팩트·고정 폭 메뉴바 아이콘**을 유지한다. 고급 자동화·조건 편집·원시 진단은 접힌 상세와 편집 화면에 배치한다.

기본 화면에서는 현재 유지 이유/시간, 시작·종료·모두 중지의 범위, 덮개·전원 분리 결과를 먼저 보여준다. 다음 수동 선택과 현재 수동의 연장을 구분한다. 같은 상태·설명·시간을 여러 곳에 중복하지 않는다.

기본 메뉴는 현재 결과·주 조작을 먼저 두고 조건 편집·도우미/타사 영향·원시 기록은 상세로 분리한다. 수동 시작/수동만 종료/모두 중지/재개의 범위를 글자로 설명하고, 다음 시간 선택이 현재 타이머 재시작처럼 보이지 않게 한다. 아이콘은 대기·유지·중지/제한을 폭 변경 없이 구분하며 원격 연결 표시를 중복 추가하지 않는다. 남은 시간은 패널과 툴팁에서 제공한다. 기본 표시는 ‘27분 남음’처럼 짧게 하되 만료 1분 이내에는 초를 표시하고 정확한 마감은 함께 확인할 수 있게 한다. 표시 반올림이 실제 기한을 바꾸지 않으며 1분 이상은 올림 표시로 조기 만료처럼 보이지 않게 한다. 실행 중 ‘다음 수동 시간’은 기타/상세로 옮기고 현재 시간·연장·수동만 종료·모두 중지를 우선한다.

규칙 예행연습은 고급 규칙의 ‘예행연습…’, 이력은 앱 설정의 ‘설정 변경 이력…’, 설치 예약은 업데이트 상세에 배치한다. 예약 대기/취소 사유·원복 실패처럼 현재 조치가 필요한 상태는 접힘 밖에서도 표시한다. 만료 예고와 종료 알림은 작업 유지의 수동/알림 상세에서 독립 선택한다. 예행연습의 가상값/마지막 확인값과 결과 출처, 되돌리기의 변경 전후/선택 항목/실행 영향, 알림의 연장 가능/상한/옛 액션 거절을 시안에 포함한다. 기본 4화면과 설정 3탭은 유지하며 별도 편집·상세 시트는 본문만 스크롤한다.

macOS 26의 native 메뉴·Picker·Switch·Disclosure와 Liquid Glass를 우선 사용하되 본문 전체를 투명하게 만들지 않는다. 헤더·스크롤 경계에서 본문 겹침/잔상, 잘리는 포커스·선택 영역, 긴 문구의 정렬을 시안 인수 대상으로 둔다. 새 디자인 라이브러리 도입은 별도 필요성·호환성 검토 전에는 결정하지 않는다.

기능별 기본/활성/중지/보호/권한 없음/관측 미확인/실패, 펼침/스크롤 끝, 밝고 어두운 화면, 긴 한영 문구를 시안과 구현 검수에 포함한다. 확장 UI는 사용자 승인 시안을 기준으로 앱에 구현하며 정적 렌더와 실제 native 조작을 구분해 검증한다. 색·아이콘만으로 상태를 구분하지 않으며 키보드 조작·포커스·접근성 이름을 유지한다. VoiceOver 전용 확장은 추가하지 않는다.

### 사용자가 알 필요 없는 내부 상태

2026-10-15 사용자 추가 지침에 따라 **알 수 없는 원인을 추정해 표시하거나 그 가정만을 위한 기능을 만들지 않는다.** 사용자 선택과 현재 결과에 영향 없는 미확인은 별도 상태 카드·옵션·알림·재시도 흐름으로 늘리지 않는다. 사용자에게 내부 세대·owner·TTL·토큰·원복 저널 상태를 직접 판단하거나 입력하도록 요구하지 않는다.

실제 결과가 시작 불가·유지 종료·설치 보류라면 그 결과만 짧게 표시하고, 앱이 확인한 해결 수단이 있을 때만 ‘전원 확인/설정 열기/다시 확인’을 제공한다. 원인을 확인하지 못했으면 ‘다른 앱/사용자/기기 때문에’라고 단정하지 않는다. 내부의 기존 분리·마감·보호·자체 해제 규칙을 생략해 미확인 상태의 유지를 새로 허용한다는 뜻은 아니다.

시안의 손상·인증·마감 변경·관측 끊김 등을 만드는 **검토용 장면 선택기는 제품 UI가 아니다.** 제품처럼 그린 창 밖에 접어서 두고, 일반 사용자 화면과 개발 검토 도구를 구별한다. 규칙 예행연습의 가상 전원·덮개 사건 선택은 실제 관측·설정 적용과 계속 구분한다. 메뉴의 유지 이유와 설정 변경 이력을 같은 탐색으로 연결하지 않으며, 이미 보이는 이유의 중복 지름길은 생략한다.

### 12.1. 제공자와 작업 이벤트 추천

아래 ‘1차’는 구현·검증 우선순위이며 현재 지원 완료가 아니다. 타 앱의 대상 이름을 그대로 지원 목록으로 가져오지 않는다.

| 대상 | 추천 범위 | 표시·권한·실패 계약 |
|---|---|---|
| 일정 | 1차: EventKit에 노출된 사용자 선택 캘린더. `시작 ≤ 현재 < 종료`, 종일·취소 일정 제외 | 시스템은 **full access**를 요구하며 읽기 전용 권한이라고 안내하지 않음. Tether는 선택 범위의 시간/상태만 읽고 일정 쓰기·제목/메모/참석자/URL 기록은 하지 않음. 권한 취소·캘린더 삭제는 미확인/대상 없음으로 구분 |
| 회의 | 실험: 선택 앱의 마이크 입력 IO, 별도 전역 카메라 사용 조건 | ‘입력 IO 활성/카메라 사용’으로 표시. 전역 카메라 상태를 특정 앱에 귀속하지 않음. Zoom/Teams/Discord/FaceTime·브라우저는 검증 후보이며 회의 지원 확정 목록이 아님. 브라우저/보조 프로세스 귀속 검증 없이 Meet 탭·실제 참석을 단정하지 않음 |
| 미디어 | 실험: 선택 앱의 출력 IO 활성 | ‘오디오 출력 활동’으로 표시. 출력 IO/장치 점유는 음악 재생·가청 출력의 증거가 아님. 녹음/녹화·오디오 탭을 만들지 않으며 조회 권한이 전혀 필요 없다는 보장도 하지 않음 |
| 다운로드 | 1차: 연결한 다운로드 명령/작업의 명시적 종료. 실험: 선택 폴더의 Chromium `.crdownload`·Safari `.download`·Firefox `.part` | 부분파일은 진행 추정. 30초 종료 유예·300초 무변화 한도를 실험 초깃값으로 검토하되 ‘완료 성공’이 아니라 관측 종료/미확인으로 표시. 접근 실패·파일 소실·조용한 네트워크 대기를 성공으로 바꾸지 않음. `.tmp` 전체 감시와 미선택 폴더 탐색은 제외 |
| AI·빌드 | 1차: 도구와 무관한 로컬 CLI·구조화 상태 이벤트, 명시적 일회성 명령/PID | 직접 보고와 활동 추정 구분. transcript·채팅 DB·프롬프트·전체 명령 인수/출력은 읽지 않음. Claude Code/Codex/Cursor 전용 자동 감지·MCP 서버·hook 자동 설치는 보류 |

캘린더·선택 폴더 등 권한은 사용자가 해당 조건을 준비할 때만 요청한다. AC 재연결·자동 조건 재평가·앱 로그인 시작이 새 권한창을 자동으로 띄우지 않으며, 누락 권한은 해당 조건의 `권한 필요`로 표시한다. 다른 정상 묶음·수동을 막거나 권한 오류를 단순 AC 조건으로 바꾸지 않는다.

작업 이벤트는 heartbeat **30초**, 기본 TTL **120초**, 허용 TTL 최대 **300초**, 응답 대기는 진입부터 **5분**을 제품 추천으로 둔다. 응답 대기 마감은 heartbeat로 초기화하지 않는다. 유휴·명시적 종료는 해당 요구를 즉시 해제한다. 관측 만료는 작업 성공이 아니다. 자동 입력은 AC에서만 유효하고 배터리 수동/PID는 기존 수동 마감과 최초 시작+120분을 따른다.

AC 자동 이벤트의 정상 heartbeat 중에 새 2시간/8시간 총상한은 강제하지 않는 것을 추천한다. 일반 AC 자동에 없는 마감을 AI 작업에만 부여하면 장시간 빌드를 예기치 않게 끝낼 수 있기 때문이다. 유효 마감은 `마지막 수신+TTL / 사용자가 선택한 고정 마감 / 응답 대기 마감 / 종료·분리·보호·Sleep` 중 해당하는 가장 이른 값이다. TTL이 지난 요청은 종료하며 같은 ID의 늦은 heartbeat로 부활하지 않는다. 새 시작은 현재 소유자·전원 세대에 맞는 새 요청이어야 한다.

근거: [EventKit 전체 접근 요청](https://developer.apple.com/documentation/eventkit/ekeventstore/requestfullaccesstoevents%28completion%3A%29), [선택 캘린더 이벤트 조회](https://developer.apple.com/documentation/eventkit/retrieving-events-and-reminders), [장치 사용 상태](https://developer.apple.com/documentation/avfoundation/avcapturedevice/isinusebyanotherapplication), [입력 IO](https://developer.apple.com/documentation/coreaudio/audiohardwareprocess/isrunninginput)·[출력 IO](https://developer.apple.com/documentation/coreaudio/audiohardwareprocess/isrunningoutput), [파일 변경 알림](https://developer.apple.com/documentation/foundation/nsfilepresenter/presenteditemdidchange%28%29). 참고 코드: [CalendarActivity](../../../../power-app-reference-sources/keepresso/Sources/KeepressoCore/CalendarActivity.swift), [MediaActivity](../../../../power-app-reference-sources/keepresso/Sources/KeepressoCore/MediaActivity.swift), [DownloadWatch](../../../../power-app-reference-sources/keepresso/Sources/KeepressoCore/DownloadWatch.swift), [AgentHooks](../../../../power-app-reference-sources/keepresso/Sources/KeepressoCore/AgentHooks.swift), [AutomationLease](../../../../power-app-reference-sources/keepresso/Sources/KeepressoCore/AutomationLease.swift). ### 12.2. 보호와 관측 주기 추천

이하 숫자는 **Tether 초기 추천값**이다. Apple은 각 조회·변경 알림의 의미를 제공하지만 20%·15초·CPU 임계값을 공통 안전 기준으로 정하지 않는다. 구체 주기는 기능이 켜지고 필요할 때만 적용하고, 비활성 조건을 계속 polling하지 않는다.

| 항목 | 추천값 | 경계·이유 |
|---|---|---|
| 배터리 하한 | 20/25/30/40/50%, 기본20%, OFF 없음 | 시작은 하한 초과에서만, 실행 중 하한 이하 종료. 더 엄격한 기존55~80% 값은 보존/표시하며50%로 낮추지 않음 |
| 전원·열·활성 소유·필요한 배터리/LPM | 변경 알림 즉시 재조회, 시작/연장/갱신 전 확인. 활성 중5초 재확인·마지막 유효 관측 최대15초 | 5초 주기의 세 번 누락을 초기 한도로 두되 보호/분리가 이미 확인되면 기다리지 않음. 실패를 새 표본으로 timestamp 갱신하지 않음 |
| 앱/프로세스·네트워크·기기 조건 | 가능한 변경 알림 우선, 활성 조건10초 재조회·유효기간30초 | 개별 실패는 해당 조건에 한정. 필요하지 않은 권한·장치를 상시 조회하지 않음 |
| 일정 | 변경 알림/다음 시작·종료 경계/시계 변경 때 재평가, 활성 중60초 재조회·유효기간120초 | 벽시계 구간만 재평가. 놓친 과거 시작 소급·수동 마감 변경 없음 |
| CPU·전송량 | 실험 초깃값: 2초 표본·10초 평균·조건 해제30초 유예 | CPU는 전체 논리 CPU 대비0~100%로 정규화, 기본20%. 전송은1MiB/s 기본 후보. 사용자 작업/기기에 따라 검증·조정하며 완료 증거로 쓰지 않음. 유예는 분리/보호/중지에 적용 금지 |
| 유휴 후 화면 유지 해제 | 기본 OFF, 선택5/10/15/30분 추천 | 해당 요청의 화면 요구만 해제. 입력 내용은 읽지 않음. 유휴 관측 미확인으로 시간 경과를 추정해 화면을 끄지 않고 제한을 표시. 키보드/포인팅 관측과 원격 입력 지원 범위는 제공자 인수 대상 |

표본 유효기간15초와 도우미 실행 허가 최대30초는 다른 제한이다. 실행 허가는 필요한 유효 표본의 마감을 넘길 수 없다. 이15초는 기존 GUI 관측30초/health lease90초를 그대로 복사하지 않은 더 보수적인 추천이며, 활성 시 호출 비용·스케줄 지연·오탐 종료를 확인한 뒤 확정한다. 새 부팅·FullWake에서는 필요한 표본을 다시 확보한다.

### 12.3. 실행·연장·원복 시간 예산 추천

| 제한 | 추천값·관계 | 실패 때의 결과 |
|---|---|---|
| 실행 허가 | 최대30초, 10초마다 갱신. 자원을 정당화하는 유효 요청/조건·필수 표본의 수명을 넘지 않으며 아래 합성 규칙 적용 | 이벤트 TTL·응답 대기·시간표 끝·수동 마감·배터리 최초+120분 포함. heartbeat로 표본·사용자 마감·종료 세대를 갱신하지 않음 |
| 명령 전체 응답·연장 승인 | 전체5초 또는 현재 요청 마감 중 먼저. 재시도 단계마다5초 재시작 금지 | 시간 초과는 처리 미확인일 수 있음. 같은 ID 현재 상태 조회·늦은 적용의 회수, 새 ID 자동 시작 없음 |
| 원복 1회 계획예산 | writer2초 + 종료 유예0.2초 + 종료 확인0.5초 + 재조회1초 ≈4초 | OS 실행 완료 보장이 아님. signal/timeout만으로 writer 종료를 확인한 것으로 처리하지 않음 |
| 종료 전용 Sleep 권한 | 사건 T부터30초. 사건 당시 유효 요청에서만 발급. 예정 만료는 원래 마감, 분리는 현재 세대의 관측 사건 시각에 고정 | 늦게 처리했거나 만료한 실행 허가를 발견했다고 새30초를 부여하지 않음. payload 날짜로 권한 연장 금지·만료/재연결/새 유효 요청/소유자 변경 뒤 과거 Sleep 재생 없음 |
| 원복 재시도 | T+0/5/10/20초 최대4회. 이미 지난 슬롯을 뒤늦게 몰아서 실행하지 않음 | 이전 writer 종료 확인·현재 소유 자원 확인 전 다음 writer 금지. 유효 권한·남은 예산이 없으면 새 Sleep 요청 금지 |
| 권한 만료 후 복구 | 미완료 자체 원복 저널 보존, 실행 중 복구 미완료일 때30초 간격 재확인 후보 | 같은 실패를 매번 알리지 않음. 타사 자원/소유 불명은 자동 덮어쓰기 없음. 원복 확인과 Sleep 권한을 분리하고 옛 Sleep은 재생하지 않음 |

먼저 요청별 유효 마감을 `해당 표본/조건 만료·이벤트 TTL·응답 대기·시간표 끝·선택한 마감·적용되는 배터리 상한` 중 이른 값으로 제한한다. 그 다음 일반/화면/덮개 **자원별로 그 자원을 요구하는 유효 요청을 합성**한다. 허가 마감은 `현재+30초`와 해당 자원을 정당화하는 요청별 마감 중 가장 늦은 값 중 이른 때다. 유효 요청이 하나도 없으면 즉시 해제한다. 따라서 마지막 이벤트의 TTL 뒤에 허가만 남지 않으며, 다른 정상 AC 요청이 남아 있으면 그 요청의 범위는 유지한다. 분리·보호·전체 중지는 기존 요청을 먼저 소비하므로 합성으로 우회하지 못한다.

정상 계획에서는 마지막 원복이 약 T+24초에 끝나므로 최종 전원/덮개/소유/권한 확인의 여유가 있다. 하지만 OS/파일 I/O·프로세스 종료가 지연되면 **30초 내 원복·실제 Sleep 성공을 보장하지 않는다**. 권한 만료 후에는 검증된 자체 정리만 허용한다. 원복 재조회·저널 기록 이후에도 OS 호출 직전에 최신 기한/취소 조건을 재검사한다. Sleep 통지 콜백에서 이 재시도 예산을 기다리지 않는다.

보완 전 코드의 원복30초 재시도와 Sleep 권한30초를 그대로 조합하면 첫 재시도가 권한 끝에 걸리는 문제가 있었다. 이는 위 시간표를 함께 정한 조사 근거이며, 현재 [원복 재시도](../../../Sources/TetherHelper/Helper+LidExecution.swift)와 [Sleep 권한](../../../Sources/TetherCore/Policy/SleepRequestPolicy.swift)의 구현·자동 회귀 근거는 [v4 구현·검증 결과](../../IMPLEMENTATION-V4-20261015.ko.md)를 따른다. [writer 기본2초](../../../Sources/TetherCore/IPC/PowerWriterJournal.swift)·[종료 확인](../../../Sources/TetherCore/System/Shell.swift), 경쟁 앱 [OpenLid 응답5초](../../../../power-app-reference-sources/openlid/crates/app/src/helper_client.rs)·[Amped 응답5초](../../../../power-app-reference-sources/amped/Sources/HelperClient.swift)는 비교 근거다. 도우미의 유휴 종료15/30초는 별개 수명이며 원복 보장 시간으로 가져오지 않는다.

공식 근거는 [수면 포함 연속 시계](https://developer.apple.com/documentation/kernel/1646199-mach_continuous_time), [assertion timeout](https://developer.apple.com/documentation/iokit/kiopmassertiontimeoutkey), [Sleep 통지 응답 절차](https://developer.apple.com/library/archive/qa/qa1340/_index.html), [IOPMSleepSystem의 요청·호출자 조건](https://developer.apple.com/documentation/iokit/1557121-iopmsleepsystem)이다. assertion timeout 지원을 전역 `SleepDisabled`의 자동 원복 보장으로 확대하지 않는다.

### 12.5. UPS·시스템 진입점·UI 추천

- UPS 백업은 첫 v4에서 새 유지 지원을 보류하고 기존 AC 요청을 소비한다. 정상 AC 데스크톱은 내장 배터리/덮개가 없어도 지원하며 도우미를 요구하지 않는다. UPS 연결 여부와 실제 공급 출처의 조합·관측 실패는 실제 장치 인수 뒤 범위를 확대한다.
- 조작 진입점은 CLI/Shortcuts/App Intents를 공통 명령으로 먼저 연결한다. 그 뒤 제어 센터는 명시적으로 이름 붙인 ‘AC 자동’ 제어 하나, 위젯은 마지막 확인 상태·시각과 앱 열기/공통 조작을 작은 범위로 제공하는 안을 추천한다. 전체 중지/보호는 토글로 암묵 해제하지 않는다.
- WidgetKit 위젯은 상시 실행되지 않으며 timeline 갱신 시각도 보장되지 않는다. **위젯은 마감·heartbeat·원복 실행기가 아니다.** Control은 timeline과 갱신 방식이 다르지만 역시 독립 전원 실행기가 아니다. 표시 캐시와 실제 상태를 구분하고 실제 조작 시 최신 상태로 명령을 검증한다. 소유 앱에 연결할 수 없으면 처리 미확인/앱 열기를 제공하며 옛 시작을 큐에 쌓아 재생하지 않는다.
- 공식 Controls 문서와 현재 macOS27 SDK의 `ControlWidget` 선언에서 macOS26 가용성을 확인했다. SDK 선언 확인은 macOS26 실기기 노출·서명/패키징·권한·백그라운드 동작 인수가 아니다.
- UI는 기존 그래파이트+블루·작은 native 조작·헤더/스크롤 경계·접힌 고급 상세를 유지한다. 준비 중·시작 거절/부분 회수·표시가 오래됨·실험 제공자·UPS 제한 상태는 승인 시안을 기준으로 구현·검증한다. 새 UI 라이브러리는 채택하지 않으며 구현 승인과 실제 native 인수 완료는 구분한다.

공식 근거: [Controls와 App Intents](https://developer.apple.com/documentation/widgetkit/controls-collection), [위젯 갱신 예산](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date), [timeline 시각의 한계](https://developer.apple.com/documentation/widgetkit/timeline), [Intent 실행 모드](https://developer.apple.com/documentation/appintents/appintent/supportedmodes). 현재 [UPS를 unknown으로 분류하는 코드](../../../Sources/TetherCore/System/SystemProbe.swift)는 지원 완료로 확대하지 않는다.

### 12.6. 공식 보장·제품 추천·실측의 경계

- Apple의 열 상태는 섭씨 온도가 아니라 OS 압력 단계다. Low Power Mode와 저배터리 경고는 별개이며 경고가 고정 잔량/남은 시간을 보장하지 않는다. 20%·15초·30초·10분/3%p는 위에서 제안한 Tether 값이다.
- [Apple 공개 IOKit 구현](https://github.com/apple-oss-distributions/IOKitUser/blob/main/ps.subproj/IOPowerSources.c)의 `IOPSGetBatteryWarningLevel`은 내부 조회 실패 때 `None`, `IOPSGetProvidingPowerSourceType`은 일부 내부 실패 때 `AC`를 반환하는 경로가 있다. 최신 snapshot/description 교차 확인을 추천하지만 모든 내부 실패를 검출한다고 약속하지 않는다. 공개 소스 검토이며 설치된 macOS 바이너리의 실패 재현 결과가 아니다. API 의미는 [IOPowerSources](https://developer.apple.com/documentation/iokit/iopowersources_h)·[전원 상태](https://developer.apple.com/documentation/iokit/kiopspowersourcestatekey)·[저배터리 경고](https://developer.apple.com/documentation/iokit/iopslowbatterywarninglevel)를 따른다.
- 일반 유휴 assertion·타사 전역 차단·Apple의 외장 화면 클램쉘·도우미 기반 유지 실행을 구분한다. 공식 Sleep 요청 성공은 실제 Sleep이 아니며, 자체 원복은 타사 요청 제거가 아니다. 공식 액세서리 승인 요구를 앱이 우회하지 않는다. [Apple 외장 액세서리/닫힌 사용 안내](https://support.apple.com/en-gb/102282).
- 추천값은 가짜 시계/IPC 경합 검증 후 실제 macOS26·도우미·원격·기기별 관측 비용과 지연으로 인수해야 한다. 숫자가 문서에 들어갔다는 이유로 지원·안전·시간 내 완료를 확정하지 않는다. 물리 시험은 사용자 요청대로 나중에 수행한다.

### 12.7. 규칙 예행연습 계약

- 입력은 저장된 설정 또는 편집 중인 설정의 복사본, 마지막 관측의 읽기 전용 복사본, 사용자가 고른 가상 전원·덮개·보호·권한·시각/종료 사건이다. 실제값/마지막 확인 시각/미확인/가상 입력을 분리한다. 오래된 실제 표본을 현재 사실로 새로 찍지 않으며, 가상 ‘권한 있음’은 실제 권한 승인이 아니다.
- 같은 정책 의미로 예상 유지 이유·요청 소비·일반/화면/덮개 계획·원복 선행 조건·Sleep 요청 가능/차단 이유를 설명한다. 닫힌 분리·배터리 수동 만료와 AC 자연 종료는 §4.2를 따른다. 실제 실행 결과·실제 Sleep·원격 프레임/입력·패널 전력 확인으로 기록하지 않는다.
- 실행 어댑터를 연결하지 않은 경로에서 평가한다. assertion·도우미 제어/허가 갱신·pmset 쓰기·Sleep·감싼 명령·알림 제출·권한창·새 파일/폴더 감시·업데이트/예약·설정/이력 저장·실행/원복 저널 변경을 하지 않는다. 실제 결정 기록과 상세 수집의 성공 사건에도 섞지 않는다. 가상 시계/사건은 메모리에만 두며 기본 파일 저장이 없다.
- 예행연습 자체로 자동 ON·수동 시작·프리셋 적용·보호 해제를 하지 않는다. 닫기/취소는 가상 상태를 버린다. 실제 적용은 별도 편집 화면에서 현재 설정 세대·최신 실제 관측/권한으로 새 평가하며 가상 값이나 예전 실행 계획을 재생하지 않는다.
- 문구는 ‘예상 동작 / 실행하지 않음’으로 표시한다. 실제 시나리오 시험과 섞인 통과 배지·성공 점수는 만들지 않는다.

### 12.8. 작업 종료 후 업데이트 계약

**의미와 선택:** 사용자가 확인한 특정 버전에 ‘작업 끝나면 설치’를 선택한다. 추적 중인 수동 유지 기한 또는 연결한 작업 종료를 기다리는 기능이며, Mac 전체 작업 완료·실제 시스템 유휴 검출이 아니다. 매 버전 명시 선택, 기본 자동 예약 없음. 정상 AC에서만 예약을 승인하며 다운로드/검증·예약 대기·취소는 기존 수동/자동을 종료하지 않는다.

| 상태/사건 | 처리 |
|---|---|
| 대기 대상 | 유효한 시간제 수동/PID와 명시적 작업형 AC 이벤트, 시작/연장 승인 대기. 선택 시 대상과 현재 상태를 표시하고 교체 경계 전에 생긴 새 대상도 포함. 종료를 관측할 연결 작업 없는 무제한 수동에는 예약 설치를 제공하지 않고 ‘지금 설치’로 안내. 연결 작업이 있어 정상 종료를 관측할 수 있는 무제한 수동은 그 작업 종료를 기다릴 수 있음 |
| 대기 중 무제한 수동 시작 | 연결 작업 없는 무제한 수동이 교체 경계 전에 새로 승인되면 현재 수동은 보존하고 설치 예약 승인을 해제. 수동을 취소하거나 종료 시점을 임의로 만들지 않음. 사용자가 필요할 때 ‘지금 설치’를 별도로 선택 |
| 대기에서 제외 | 단순 AC 자동·시간표·앱/네트워크/화면/회의 조건. 이들을 실제 작업 완료로 간주하지도 않으며 무한 설치 대기의 이유로 쓰지도 않음 |
| 정상 종료 | 수동 기한의 정상 만료·관측한 연결 작업 정상/오류/취소 종료를 구분해 대기 목록에서 제거. 외부 PID 종료는 성공 판정 아님. 작업형 이벤트의 유휴/응답 대기는 종료로 보지 않음. 유지 요구가 풀려도 예약의 작업 식별/종료 확인은 별개이며 이를 위해 새 전원 허가를 만들지 않음 |
| 확인 불가·안전 소비 | 이벤트 TTL/연결 관측 만료·전원 분리·보호·모두 중지·직접 수동 종료/잠자기·실제 OS Sleep·owner 종료는 ‘작업 완료’가 아님. 예약 실행 승인을 취소하고 확인 필요 이유 표시. 실제 유지 종료·원복·Sleep은 원래 우선순위대로 즉시 처리 |
| 예약 수명 | 대상 버전/검증할 패키지 identity·채널·실행/업데이트 설정 기준 세대·현재 owner에 결속. 최대24시간을 제품 기본안으로 추천. 새 작업·heartbeat가 수명을 늘리지 않음. 재시작/로그아웃/부팅을 넘겨 설치 승인을 복원하지 않음 |
| 대상 변경 | 새 버전·채널 변경·이미 설치한 버전·패키지 검증/호환성 변경은 원래 예약을 취소/확인 필요로 둠. 다른 버전을 조용히 대신 설치하지 않음. 관련 실행/업데이트 설정 변경도 기준을 다시 보여주고 새로 선택 |
| 최종 교체 조건 | 대기 대상 없음·시작/연장 대기 없음·유효한 정상 AC/열/owner·자체 원복 미완료 없음·패키지/앱-도우미 호환성 확인. MacBook은 열린 덮개 확인 필수, 데스크톱은 덮개 해당 없음. 화면 잠금만으로 owner가 바뀌었다고 보지 않음 |
| 사용자 인증 필요 | 자동 예약에서 새 관리자 인증창을 시작하지 않음. ‘인증 후 설치 필요’로 대기하고 사용자가 설치 조작을 선택할 때 정상 인증 경로 사용. 인증 대기는 새 시작/연장 승인 제한5초와 별개 |
| 지금 설치/취소 | 즉시 설치는 끝날 자체 요청·덮개/원격 영향·수동 비복원을 보여준 뒤 별도 교체 확인. 보호/소유 미확인/원복 실패를 우회하지 않음. 닫힌 MacBook은 먼저 덮개 열기를 안내. 예약 취소는 현재 유지 요청 보존 |

실행 직전의 짧은 단일 교체 경계에서 현재 상태/설정 세대를 재검사한다. 새 요청/연장이 먼저 승인되면 설치는 다시 대기한다. 단, 연결 작업 없는 무제한 수동은 위 표대로 예약 승인을 해제한다. 교체 경계가 먼저 확정되면 새 시작/연장은 잠시 `updateBusy`로 거절하고 나중에 재생하지 않는다. 분리·보호·사용자 중지·소유자 종료는 이 경계보다 우선하며, 실제 앱 종료/권한 실행 직전에도 AC·덮개·원복·owner를 재검사한다. 닫힘/미확인/안전 사건이 먼저면 교체를 취소하고 유효한 기존 요청만 보존한다. 교체가 실제로 시작된 뒤에는 §4.4대로 수동을 소비하며 새 프로세스는 이를 복원하지 않는다.

예약은 전원 실행 허가가 아니며 끝난 요청을 설치 때까지 붙잡지 않는다. 업데이트를 위해 Sleep을 늦추거나 예약 깨우기·배터리 유지·재연결 후 옛 작업 복원을 만들지 않는다. 설정 변경 이력 되돌리기도 이 예약을 되살리지 않는다. 24시간·상태 전이의 격리 자동 회귀 근거는 [v4 구현·검증 결과](../../IMPLEMENTATION-V4-20261015.ko.md)에 연결하며 실제 설치와 프레임워크 접점의 OS 인수는 별도 후속 범위다.

### 12.9. 설정 변경 이력·선택 되돌리기 계약

- 대상은 논리적으로 적용된 앱 설정·자동 규칙·프리셋·다음 수동 기본값이다. 시각·변경 출처(사용자/가져오기/이관/되돌리기)·스키마/기준 세대·변경 전후를 제한된 로컬 영역에 기록한다. 조회·편집 중 값·무변경 저장·예행연습·센서 갱신은 새 이력이 아니다. 기본 추천은 최근20건·최대30일·총1MiB 중 먼저 도달한 한도이며 정상 측정 후 확정한다. 초과 시 오래된 완료 이력을 정리하고 개별 항목/전체 이력 삭제를 제공한다.
- 현재 요청 ID/PID·최초 시작/마감/연장 상태·전체 중지·보호 사유·실행 허가/토큰·설치 예약·OS 권한·도우미 승인·원복 baseline/미완료 저널은 이력 복원 대상이 아니다. 일반 로그와 원복 저널도 이력 삭제/보관 한도에 포함해 지우지 않는다. 프롬프트/채팅/전체 인수·화면 캡처를 이력에 넣지 않으며 자동 외부 전송/바탕화면 파일은 없다.
- 되돌리기는 미리보기에서 현재값과 차이·권한 부족·미지원/퇴역 항목·현재/다음 작업 영향·자동 ON 또는 활성 규칙 변경으로 즉시 시작/종료할 가능성을 보여준 뒤 사용자가 선택한 설정 묶음만 적용한다. 조건 그룹/프리셋처럼 의미가 결합된 변경은 함께 검증하며 알 수 없는 AND 조건을 빼지 않는다.
- 선택한 묶음 중 현재 수동의 선택·기한·실행 상한을 바꾸는 전역 변경이 있으면 해당 선택 트랜잭션의 적용을 보류한다. 영향을 주는 항목을 제외해 다시 선택하거나 수동 종료 뒤 새 차이를 확인해야 한다. ‘보류’는 나중에 자동 적용하는 예약이 아니다. 무관한 다음 기본값/앱 옵션만 선택하는 것은 가능하다.
- 미리보기와 적용 사이 설정 세대가 바뀌면 차이를 새로 계산하고 다시 적용을 선택한다. 선택한 이력이 삭제/정리되었거나 대상 내용 해시가 맞지 않아도 옛 복사본을 조용히 적용하지 않고 재선택을 요구한다. 손상·지원하지 않는 버전·이관 실패·잘못된/미지원 조건은 현재 설정을 보존하고 선택 묶음 전체를 거절한다. 내부 설정은 선택 트랜잭션을 전부 검증한 뒤 원자적으로 저장하며 실패한 일부 항목만 적용한 것으로 숨기지 않는다. 성공한 되돌리기도 새 이력이며 과거 이력이나 이후 사용자 변경을 덮어 지우지 않는다.
- 자동 ON/규칙 복원은 사용자 명시 적용 후 현재 gate로 새 평가한다. 전체 중지/보호는 그대로이고 소비한 수동/이벤트는 복원하지 않는다. OS 권한을 복원하거나 누락 권한창을 자동 호출하지 않는다. 설정 저장·일반/화면/덮개 실행·로그인 항목 등 외부 등록의 실제 결과는 별도로 표시하며 OS 효과 전체가 원자적으로 되돌려진다고 약속하지 않는다. 자체 원복 실패는 기존 보호/저널 경로로 처리한다.
- 이력 저장 실패와 설정 저장 실패를 구분한다. 이력만 실패하면 ‘이력 누락’을 표시하고 되돌릴 수 있다고 약속하지 않는다. 이력 실패가 사용자 중지·자동 OFF·분리·보호 종료를 막지 않는다. 되돌리기 설정 트랜잭션 자체의 저장 실패는 현재 설정을 보존하고 실패를 표시한다. 보관/스키마/실패 처리 수치는 저장/이관 자동 회귀와 실제 보관 인수를 구분해 검증하며 현재 근거는 [v4 구현·검증 결과](../../IMPLEMENTATION-V4-20261015.ko.md)를 따른다.

## 14. 편의 옵션 확장 요구 · 2026-10-16

사용자는 Keepresso와의 상세 비교 후 ‘다른 앱들처럼 옵션을 많이 제공’하길 요청했고, 범위 질문에는 **‘핵심 규칙 유지, 나머지 옵션 확장’**을 선택했다. 따라서 AC 자동만 허용·모든 AC 분리에서 기존 요청 종료·최초 배터리 시작+120분 상한은 그대로다. 전원 분리 후 승계·배터리 무제한·종료한 수동 자동 복원은 새 선택지로 추가하지 않는다.

이 절은 **후속 옵션 설계 범위**이며 후보58에 새 옵션이 구현됐다는 뜻이 아니다. 현재 구현/미지원 현황과 비교는 [상세 기능 대조](../../FEATURE-ADOPTION.ko.md#keepresso-1270과-후보58-상세-대조--2026-10-16)를 따른다. 추가 UI는 기존 그래파이트+블루·native 컴포넌트·설정3탭 안에서 시안을 먼저 검토한 뒤 적용한다. 설치·실제 입력·물리 시험의 기존 경계는 유지한다.

### 14.2. 옵션 간 충돌을 막는 규칙

- **유지 종료와 종료 뒤 동작은 별개다.** 현재 닫힌 분리의 `잠자기 요청/macOS에 맡김` 선택은 유지하고 어느 쪽도 기존 요청 소비를 취소하지 않는다. 다른 종료 원인 전체를 고르는 선택기는 현재 없으며, 이번 편의 확장만으로 추가했다고 표시하지 않는다.
- 새 수동 옵션은 ‘다음 요청’ 초안이다. 실행 중 화면/덮개 전역 허용을 바꾸는 기존 동작과 구분하며 현재 수동의 대상·승인 마감을 몰래 교체하지 않는다.
- 유휴 후 해제는 해당 화면 assertion 요구만 내린다. 일반 작업·덮개·수동 마감은 유지하며 다른 유효 요청이 화면을 요구하면 이를 취소하지 않는다. 입력 합성·자동 잠금 해제 기능으로 설명하지 않는다.
- 종료 옵션을 나중에 확장하더라도 마지막 유효 요청이 남은 동안 Mac 전체 Sleep·화면 종료·잠금을 자동 실행하지 않는다. 전원 분리·보호·관측 실패를 정상 작업 완료로 오인하지 않는다.
- 설정 변경·알림·단축키·외부 명령은 같은 명령/정책 경로로 연결한다. 설정 되돌리기는 설정만 복원하고 현재 요청·보호 중지·만료된 권한은 복원하지 않는다.
- 미지원 관측은 옵션만 켜서 지원으로 바꾸지 않는다. 현재 마이크·카메라·오디오 재생·다운로드는 지원 보류, CPU/전송량은 실험 옵션이다. 새 제공자는 권한·관측 정확도·비용·기기 인수를 갖춘 뒤 선택 목록에 추가한다.

### 14.3. 후속 후보와 우선 제외

Keepresso의 회의/다운로드 감지·명시적 도구 연동·위젯/제어 센터는 후속 검증 후보로 유지한다. 새 기능을 넣으려면 사용자에게 유용한 동작, 실제 관측 경로, 종료 수명, 권한, 자동·물리 검증을 함께 정의한다. 게임/팬·네트워크 전환/AWDL·NAS 주기 쓰기·private 가상 화면·가짜 키/마우스 입력은 옵션 수를 늘리기 위한 동시 채택 대상으로 삼지 않는다. 사용자 별도 요구가 있으면 목적과 영향을 검토한다.

### 14.4. 검증 추가 범위

두 닫힌 분리 동작 모두 기존 요청 종료, 자동+수동에서 수동만 종료, 요청별·전역 화면/덮개 우선순위, 유휴 후 화면만 해제, 모든 알림 OFF에서도 보호·원복, 선행 시간이 짧은 수동보다 긴 경우 무예고, 선행 시간 변경/연장/분리와 옛 알림 경합, 상한 근처 연장 거절, 새 옵션 누락 이관·기존 선택 보존을 회귀로 확인한다. 실제 UI에서는 접힘/펼침·키보드/마우스·한국어/영어·밝은/어두운 외관·최소 창·끝 스크롤·긴 이름과 메뉴바 폭을 확인한다. 이 검증은 구현 후 수행할 목록이며 현재 통과 수에 더하지 않는다.
