# 업데이트와 설정 이관

## 현재 계약 · 2026-11-11 · 빌드 60 후보

앱과 도우미의 다음 정식 후보는 **2026.11.1 · 빌드 60**이다. 서명된 고정 피드에서 정식의 더 높은 빌드만 확인하며 채널 선택 UI는 제공하지 않는다. 기존 베타 릴리스의 태그·자산은 보존한다.

예전 `updateChannel=beta` 선택과 가져온 설정의 베타 값은 정식으로 이관한다. 과거 베타 전용 피드 URL 고정값도 제거해 번들의 고정 피드를 사용한다. 자동 확인 ON/OFF, 언어·알림·전원·보호 선택은 보존하고 자동 다운로드·설치는 비활성 상태를 유지한다. 원래 사용자 설정의 백업·미완료 복구·안전 교체 검사는 계속 적용하며, 이관만으로 끝난 타이머나 작업을 다시 시작하지 않는다.

정식 전환은 낮은 빌드 설치를 허용하지 않는다. 예전 베타 설치본도 더 높은 정식 빌드를 기다리며, 이어받은 베타 업데이트 후보는 설치 대상으로 승인하지 않고 정식 재확인을 안내한다. 원본 서명·전체 패키지 교체와 관리자 도우미 갱신의 검증 범위는 [릴리스 절차](RELEASING.ko.md)를 따른다.

## 이전 검증 · 2026-10-08 · 빌드53

앱과 helper의 표시 버전은 2026.10.1, 내부 빌드는53으로 함께 올렸다. 설치본은52이며 이번 후보를 아직 실제 설치하거나 게시하지 않았다. 사용자 설정 schema·IPC protocol·덮개 coordinator 계약은 바꾸지 않았다. 이전 OFF·조건·한도·보호·언어·알림·채널 선택을 유지하고, 임시 요청을 새로 시작하는 이관은 추가하지 않았다.

Sparkle2.10.0은 자동 확인이 OFF일 때 자동 다운로드 setter를 무시하므로, 과거 `SUAutomaticallyUpdate=true`가 이후 ON에서 다시 적용될 수 있었다. 초기화 전에 이 키만 false로 고정한다. 자동 **확인** 선택과 업데이트 **채널**, 최근 확인 시각·다른 앱 설정은 보존한다. 실제 updater 시작·초기 KVO·잘못된 키·feed 없는 probe와 채널 잠금·종료를 private bundle/suite에서 검증했다. production prefs·공개 피드·실제 실행 앱을 변경하지 않는다.

이전 실제 바이너리와 모의 설치 루트의 이관·원복 및 native Sparkle 교체는 [최신 검증](VALIDATION-CHECKLIST.ko.md)에 기록한다. 이 검사와 실제 관리자 도우미 교체·앱 UI 재실행·공개 업데이트 성공은 서로 다르다. MacBook은 GUI만53으로 바꾸지 말고 도우미와 함께 확인한다. 새 관리자 인증이 필요한 단계는 [직접 조작 체크리스트](MANUAL-ACCEPTANCE.ko.md)에 남긴다. 아래 2026-10-01 빌드50/macOS15 언급은 당시 역사 기록이며 현재 지원 최소값은 macOS26이다.

## 이전 검증 · 2026-10-01 · 도우미 실행 계약 4

2026-10-01 후보 빌드 50에서 도우미 설치 완료 판정을 앱과 실제 `--check-service`에 공유했다. 버전·빌드, protocol 2, schema 3, coordinator 4가 모두 일치하고 상태 시각이 현재부터 30초 미만이어야 한다. 미래·오래된 상태, 구형·미확인 실행 계약, 이관 실패는 완료로 표시하지 않는다. 앱이 꺼져 있거나 발열 보호 중이어도 호환되는 도우미의 설치 완료 여부와 작업 유지 여부는 따로 판정한다.

자동 갱신 시도 기록은 빌드 번호에서 실행 계약 식별자로 바꿨다. 같은 후보 빌드에서도 계약이 달라지면 한 번 다시 시도할 수 있고, 같은 계약의 인증 취소·실패는 자동으로 반복하지 않는다. 수동 설치 경로는 계속 제공한다. 기존 켜기/끄기 선택과 이전 시도 기록은 보존한다.

최종 전체 Swift **708개**(Core 554 + 앱·업데이트 154, 이번 회귀 13·native 7 포함)는 실패·건너뜀 0이다. 새 포장 실행 파일의 설치 시험은 **51개**(기존 34 + readiness IPC 10 + 실제 이전 빌드 49 helper 7)가 통과했다. 수정 전 구형 계약과 미래 상태가 `helper-ready`로 잘못 승인되는 것을 실제 포장 CLI로 재현했고 수정 후 거절을 확인했다. 49→50 교체·coordinator 4 준비·실패 뒤 49 원복·임시 타이머 재생 방지도 확인했다. 처음 전체 실행의 3개 메서드/5 assertion 실패는 새 ready fixture에 schema를 명시하지 않은 검사 구성 오류였으며 fixture만 수정한 뒤 전체 재검증했다.

같은 예약의 과거 전원 전환 기록은 coordinator 4의 `continuationToken`으로 식별한다. 자동 조건·시간 변경이나 별도 수동 유지 종료가 직접 배터리 예약의 원마감을 지우지 않도록 했다. 빈 현재 유지 요청은 즉시 권한을 해제하며 과거 기록으로 작업을 새로 시작하지 않는다. 취소·새 예약·전체 중지·종료·소유권 상실은 해당 기록을 폐기한다. 포장 Workbench IPC 9·실제 CLI 3·공통 작업 25·이관 8·기기 전환 2·수동 27·조정 14개도 통과했다.

이전 바이너리와 실제 private IPC를 실행했지만 전원 효과·센서·launchd 등록은 격리 모의 경로다. 실제 관리자 설치·전체 Sparkle UI 업데이트·macOS 15 실행·물리 Sleep/Wake·자동 잠금 방지·원격 화면과 입력·장시간 내구성은 아직 미확인이다. 설치본 49와 시스템 설정은 유지했다. GitHub CLI/API 기록: [설치 판정](https://github.com/jukqaz/tether/issues/1#issuecomment-5931778780) · [예약 기록](https://github.com/jukqaz/tether/issues/6#issuecomment-5931779000). 아래의 이전 검증 횟수는 당시 근거로 보존한다.

## 사용자 동작

Tether 2026.9.1부터 앱 설정의 **업데이트 확인…**에서 새 앱을 다운로드하고 설치한 뒤 다시 시작할 수 있다. 자동 확인을 꺼도 수동 확인은 가능하다. 자동 확인 주기는 하루이며 다운로드·설치는 사용자가 선택한다.

앱 교체는 Sparkle 2.10.0이 담당한다. 공개키로 서명된 업데이트 목록과 ZIP을 검증하며 ZIP 서명 확인은 압축 해제 전에 수행한다. 시스템 프로필을 보내지 않는다. `SUFeedURL`은 `updates` 브랜치의 고정 HTTPS 주소이며 최신 정식 한 항목만 게시한다. 자동 확인 선택은 유지하고 다운로드·설치는 사용자가 승인한다. 재실행 뒤 이어받은 후보도 정식 여부를 다시 검사하며, 베타 후보는 취소하고 정식 재확인을 안내한다. 재개된 설치에서 나중에를 선택하면 종료 후 자동 설치 예약까지 취소한다.

자동 확인은 메뉴바와 앱 설정에 조용히 표시하며 팝업으로 작업을 방해하지 않는다. 자동 다운로드와 자동 설치는 제공하지 않는다. 설치 재실행 요청 때 실제 덮개 상태를 읽는다. 닫힘 또는 확인 불가면 설치를 대기하고 **덮개를 연 뒤 ‘설치 계속’**을 눌러야 진행한다. 종료 경계에서도 상태를 다시 읽어 앱이 소유한 전원 유지를 닫힌 상태에서 해제하지 않도록 한다. 관리자가 도우미 설치를 승인한 뒤에도 설치 스크립트에서 다시 확인한다. 이 검사는 OS 이벤트와 물리 동작을 원자적으로 묶지는 못하므로 실기기 전환 검증을 대체하지 않는다.

재시작 후 기존 도우미의 버전·빌드·프로토콜이 다르면 관리자 인증을 요청해 도우미를 갱신한다. 인증을 취소한 경우 앱 설정의 **업데이트 마무리…**에서 다시 진행한다. 앱 버전 문자열이 같아도 빌드가 다르거나 옛 도우미에 빌드 번호가 없으면 갱신 대상이다.

온라인 업데이터가 없는 2.0.0·2.0.1에서 전환할 때는 **최초 한 번 수동 앱 교체가 필요**하다. 앱을 교체한 뒤에는 새 앱이 기존 설정과 도우미를 이어받는다. `local.tether` 번들 ID를 쓰던 더 오래된 개발판도 아래의 환경설정 이관 대상이다.

| 설정·상태 | 업데이트 때 처리 |
|---|---|
| 사용자의 켜기/끄기 | 그대로 유지. 꺼져 있던 앱을 켜지 않음 |
| 배터리 하한·시간·전원 조건 | 보존. 예전 자동 잔량/시간 한도는 더 엄격한 값으로 고정 |
| 섭씨 온도 제한 | 원본 백업 후 제거. 명시적 설정을 쓰던 세션은 새 기준 확인 후 재개 |
| 저전력 보호 선택 | 새 정책에서는 제거. 과거 원복 기록은 계속 복구 |
| 상세 로그 선택 | 보존 |
| 언어, 메뉴바, 알림, 자동 업데이트 확인 | 보존. 새 환경설정이 이미 있으면 그 값이 우선하며 `false`도 유효한 선택으로 취급 |
| 예전 베타 채널·베타 전용 피드 | 정식 단일 피드로 이관. 가져온 베타 설정도 정식으로 저장하며 자동 확인 선택은 보존 |
| 로그인 실행 | 기존 설치의 꺼짐 선택을 기본값으로 다시 켜지 않음. 켜져 있던 실행 경로는 새 앱 위치로 갱신 |
| 밝기 복원용 과거 저장값 | 한 번 복원할 수 있도록 보존 |
| 실행 중인 임시 타이머·즉시 잠자기 요청 | 이관 시 폐기. 업데이트/재시작으로 다시 실행하지 않음 |
| 제거된 2.1 개발판 프로필·일시 중지 | 비활성 상태로 이관. 작업·규칙은 되살리지 않음 |
| 보호 중지 사유·같은 부팅의 배터리 예산 | 유지 |
| 알 수 없는 미래 schema·손상된 설정 | 기본값으로 덮지 않고 업데이트/활성화를 중단 |
| 이관 후 새로 바꾼 설정 | 재실행해도 과거 원본으로 다시 덮지 않음 |

원본 `control.json`은 변환 전 바이트 그대로 `/Library/Application Support/Tether/migrations/control-schema…json`에 0600으로 남긴다. 내용 해시가 파일명에 포함되어 서로 다른 옛 설정을 덮어쓰지 않는다. 일상적인 설정 저장의 `control.json.backup`과 별개다. 이관 보고서는 `migration-report.json`이며 앱 설정에서 완료 여부를 표시한다.

앱 환경설정은 사용자 Library의 `Application Support/Tether/migrations/preferences-before-2.2.plist`에 백업한다. 현재·이전 도메인이 모두 비어 있으면 백업 파일이나 디렉터리를 만들지 않는다. 기존 백업은 안전한 일반 파일이며 구조와 원본 값이 같을 때만 재사용한다. XML·binary plist 모두 인정하지만 다른 원본, 손상된 구조, symlink는 덮지 않고 이관을 중단한다. `false`와 숫자 `0`도 구별한다. 새 파일은 배타적으로 생성하고 0600으로 기록·동기화한다. `local.tether` 원본 도메인을 삭제하지 않는다. 백업 실패 시 원본·대상 도메인을 변경하지 않고 이관 오류를 표시한다. 일반 세션 조정자와 명령 목적지를 연결하기 전에 초기화를 중단하므로 설정·온보딩·URL·세션 시작도 거절한다. 예약한 명령 서버는 중지하며 실행 잠금은 앱 수명 동안 유지한다. 오류 상태에서도 정상 종료할 수 있다.

로그인 항목의 최초 설정과 이동된 앱 경로 갱신은 공통 작업·기존 도우미 경로 모두에 적용한다. 이관된 꺼짐 선택은 유지하고, 이미 켜진 항목만 새 실행 경로로 갱신한다. 실제 사용자의 LaunchAgent 파일 갱신은 이번 격리 시험에서 실행하지 않았다.

사용자 소유 세션의 `userOwnedSessionSettings`는 빌드 50 후보에서 v1/v2/v3→v4로 이관한다. 기존 꺼짐·자동 선택/조건·보호 중지·같은 부팅의 소비된 배터리 예산과 더 엄격한 제한을 보존하며 임시 세션·예약·마감은 재생하지 않는다. 변환 전 원본 바이트를 별도 백업하고 원본이 다르면 기존 백업을 덮지 않는다. 미래/손상/예상 밖 제한은 덮지 않는다. 이 별도 환경설정 버전은 root schema 3·IPC protocol 2와 다르다. 도우미 연결은 활성 유지를 만들지 않는 준비 ACK 뒤 현재 epoch/revision을 재조회하며, 오래된 연결이 최신 중지를 되돌리지 않도록 한다. [설정 v4·연결 인계와 검증 범위](SESSION-HANDOFF-20261001.ko.md), [초기 사용자 세션 이관 기록](USER-SESSION-INPUT-20261001.ko.md).

## 도우미 교체와 복구

1. 도우미 설치 대상인지 먼저 확인한다. 데스크톱은 기존 사용자 세션 실행 경로를 사용하고 도우미를 설치하지 않는다. 관측 불명확·미지원 플랫폼이면 교체를 보류한다. MacBook은 덮개 열림과 새 복구 실행기의 파일 안전성·기능 응답 및 새 도우미의 기존 설정 읽기를 검사한다. 기존 서비스 종료 직전에 기기·덮개를 다시 검사하며, 실패하면 기존 프로세스·파일을 바꾸지 않는다. [기기별 설치 판정](INSTALL-TARGET-20261001.ko.md).
2. 도우미·감시 장치·복구 실행기·복구 라이브러리와 launchd plist를 전용 복구 폴더에 보관한다.
3. 기존 도우미를 종료해 자신의 전원 변경을 정리한 뒤, 마지막 설정 상태와 변경 기록을 백업한다. 남은 전역 값은 유효한 현재 부팅의 Tether 기록이 있을 때만 해제한다.
4. 새 도우미·watchdog·복구 실행기·복구 라이브러리를 설치하고 서비스를 시작한다. 새 도우미가 설정을 이관한다.
5. 소켓 응답에서 현재 버전·빌드, protocol 2, schema 3, 최신 상태를 확인한다. 명령 종료 코드만으로 성공 처리하지 않는다.
6. 시작·이관·준비 확인이 실패하면 이전 바이너리, plist, 설정을 복구하고 기존 서비스를 다시 시작한다. 복구 사본은 `upgrades/helper-…`에 남는다.

빌드 50 후보에서는 복구 중 이미 소비한 `power-ownership.json`을 옛 설정처럼 되살리지 않는다. OS 해제가 확인된 후 새 watchdog 시작이 실패해도 사용자의 설정과 이전 바이너리만 복구하며, 종료된 전원 lease를 재생하지 않는다. 미완료 작성자 기록도 설정 백업으로 덮지 않는다. 공통 복구 lock을 얻고 작성자의 종료를 확인한 뒤에만 후속 전원 변경을 진행한다. 이전 helper에는 기존 `--validate-settings` 경로로 복구 기능을 확인해 알 수 없는 새 인자가 서비스를 시작하는 부작용을 피한다. [작성자 복구의 검증 범위와 제한](POWER-WRITER-RECOVERY-20260930.ko.md).

watchdog·설치·제거의 고정 복구 명령은 별도 실행기가 작성자 journal을 남긴다. 독립 실행기를 쓸 수 없으면 검증된 helper 복구 모드만 사용하며 둘 다 없으면 교체·복구를 중단하고 자료를 남긴다. [복구 실행기와 최신 포장 검증](RECOVERY-EXECUTOR-20260930.ko.md).

새 전원 작성자는 PID·시작 신원 저장 뒤에만 시작을 허용하는 `power-writer-gate-v2` 경로를 사용한다. journal schema 1의 선택 필드만 추가하며 기존 설정 schema를 바꾸지 않는다. 이미 존재하는 구버전의 미확인 작성자를 추정해 종료하지 않는 규칙은 유지한다. [시작 순서와 최신 회귀](WRITER-GATE-20261001.ko.md). v2는 새 유지·화면/시스템 잠자기를 실행하기 직전에 현재 GUI 권한을 확인한다. v1을 새 실행기로 인정하지 않으며 해제·원복은 GUI 권한 상실 후에도 허용한다. [호환성과 실행 회귀](GUI-WRITER-GATE-20261001.ko.md).

앱 교체와 관리자 도우미 교체는 서로 다른 권한 단계다. 도우미 갱신을 취소하거나 실패하면 새 앱에서 미완료 상태를 표시한다. 실제 관리자 권한의 launchd 교체는 대상 Mac에서 별도로 검증해야 한다.

빌드 50의 GUI 소유자 필드는 선택적으로 추가했다. 이전 상태의 PID/UID/start로 현재 GUI 로그인을 추정하지 않으며 새 앱의 커널 소켓 핸드셰이크로 재연결한다. 승인된 UID와 명시적 끄기 선택을 보존하고 임시 타이머/예약은 재생하지 않는다. 설정 schema 3·IPC protocol 2를 유지한다. [GUI 권한 이관의 시험 범위와 남은 관리자 검증](GUI-AUTHORITY-20261001.ko.md).

`Package.resolved`는 Sparkle 2.10.0과 공식 바이너리 체크섬을 고정한다. `Resources/update-public-key.txt`와 `Info.plist`에는 공개키만 있다. 개인키는 저장소·ZIP·패치에 포함하지 않는다.

## 수명 주기와 제거

종료가 취소되는 실패에서는 일반 작업 조정자를 먼저 끝내지 않는다. 자체 도우미 해제 효과를 확인하고 업데이트의 현재 덮개 상태를 다시 읽은 뒤 native 요청을 해제한다. 실패 시 같은 일반 세션·원래 마감·소비 예산을 유지하되, 대기 중 실제 정책이 만료시킨 임시 세션은 복원하지 않는다. native 해제 실패는 같은 ID로 재시도하며 종료 중인 조정자는 새 도우미 lease를 발행하지 않는다. 소켓 중지와 종료 승인만으로 앱 실행 잠금을 넘기지 않는다. 전체 Swift 555개(native 7개 포함)와 후보 포장은 확인했지만 실제 Sparkle·관리자·물리 종료 경계는 남는다. [종료 계약·재현·검증 범위](UPDATE-TERMINATION-20261001.ko.md).

현재 schema 3과 protocol 2를 사용한다. GUI·도우미·설치기의 준비 확인은 `Control.currentSchema`를 공유한다. 앱은 도우미 빌드까지 일치해야 정상 제어한다. 앱의 정상 종료·업데이트 재실행에서도 임시 유지와 예약은 이어받지 않는다. 저장된 사용 여부와 전원 조건은 보존한다. 실제 Sparkle UI → 앱 재시작 → 관리자 도우미 교체 전체 경로는 실 설치에서 확인해야 한다.

제거기는 도우미 종료를 먼저 기다리고, Tether 변경 기록을 확인한 다음 해제한다. 저전력 복원 기록이 남거나 명령이 실패하면 파일을 보존하고 실패를 반환한다. 격리된 실제 제거 스크립트로 소유/비소유, 이전 부팅, 복원 미완료, 명령 실패, 도우미 미종료, 다른 CLI 링크 보존을 검증한다.

GUI의 완전 제거도 일반 종료 계약으로 도우미 detach와 native 해제를 확인한 뒤 삭제를 시작한다. 해제 실패나 효과 미확인은 제거를 시작하지 않는다. 로그인 항목은 없는 파일만 성공으로 처리하며 권한 등 실제 오류는 그대로 표시한다. 앱의 휴지통 이동 완료를 기다린 후 환경설정을 지우고 종료한다. 인증 취소·중간 실패는 설정을 보존하며 유지 요청을 다시 만들지 않고 재시도할 수 있다. 휴지통 이동 대기 중 중복 제거·종료를 거부하고 완료 뒤에는 삭제된 도우미에 다시 접속하지 않는다. 8개 GUI 제거 회귀는 주입한 효과로 확인했으며 실제 설치 앱 제거·관리자 인증·사용자 휴지통 이동은 실행하지 않았다.
