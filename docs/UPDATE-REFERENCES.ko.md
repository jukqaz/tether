# Tether 업데이트 참고 조사와 적용안

조사일: 2026-09-28. 공식 문서·공개 소스·제작자 저장소의 이슈를 확인했다. 타 앱을 설치해 전체 업데이트를 실험한 결과는 아니다. 아래의 ‘Tether 적용안’은 조사에서 도출한 설계이며 아직 구현·배포 완료를 뜻하지 않는다.

## 결론

정식/베타 선택은 IINA·1Password, 채널 복귀는 Ghostty, 방해하지 않는 알림은 Lunar, 현재/새 버전과 진행 표시는 Stats에서 참고한다. 파일 검증·다운로드·교체는 현재 사용 중인 Sparkle에 맡긴다. Tether는 여기에 **닫힌 덮개에서 업데이트를 위해 작업 유지를 끊지 않는 정책**, 관리자 도우미 갱신과 설정 이관 확인을 추가해야 한다.

## 확인한 사례

| 앱 | 확인한 사실 | Tether에 가져올 부분 |
|---|---|---|
| IINA | `receiveBetaUpdate` 기본값은 false. 선택에 따라 업데이트 피드를 바꾸며 시작 때 과거 UserDefaults 피드 주소를 정리한다. | 명시적인 베타 선택, 기존 채널 선택 보존, 이전 피드 설정의 이관 |
| Ghostty | stable/tip 채널을 제공한다. 기본 채널은 설치한 바이너리 채널을 따르며, stable로 바꿔도 더 새로운 정식이 나올 때 반영된다. 즉시 구버전 복귀는 수동 재설치다. | 설치한 버전과 앞으로 받을 채널을 구분. 정식 전환을 다운그레이드와 혼동하지 않는 안내 |
| Lunar | Sparkle gentle reminder를 사용한다. 예약 검사에서 표준 창을 즉시 띄우지 않는 경우 새 버전 표시를 남기고 세션 종료 때 지운다. | 작업 중 포커스를 빼앗지 않는 앱 내부 업데이트 표시, 수동 검사 때 명확한 창 표시 |
| 1Password | 설정에서 배포 채널을 고른다. 자동 설치가 켜져 있어도 잠금/사용 상태에 따라 자동 설치와 안내를 구분한다. | 확인·다운로드와 실제 재시작을 구별하고 앱의 현재 작업 상태를 고려 |
| Stats | 현재·최신 버전, 다운로드 진행률, 설치 단계를 표시한다. 업데이트 검사 중복을 제한하고 별도 배포 서버 실패 시 GitHub 조회를 시도한다. | 버전 비교·오류 단계·재시도 표시. Tether의 검증된 피드를 우회하는 무서명 대체 경로는 추가하지 않음 |

## 사용자 이슈에서 얻은 교훈

Ghostty 사용자 보고에는 `auto-update-channel = tip`을 지웠는데 계속 tip을 받는 사례가 있다. 공식 문서상 기본 채널은 현재 바이너리를 따르므로, 설정을 삭제하는 것과 stable을 명시하는 것은 다르다. 이를 현재 제품 결함으로 단정하지 않는다. Tether는 `정식`을 선택하면 명시적인 값으로 저장하고 다음 검사부터 적용해야 한다. 베타 바이너리가 사용자 선택을 다시 베타로 덮어쓰지 않도록 한다. [사용자 보고](https://github.com/ghostty-org/ghostty/discussions/11476), [공식 기본값](https://ghostty.org/docs/config/reference#auto-update-channel).

BetterDisplay의 과거 정책처럼 베타 바이너리에서 선택과 무관하게 베타를 강제하는 방식은 채택하지 않는다. 신규 베타 설치 시에는 베타 수신 의도를 분명히 알리고, 이후 사용자가 정식으로 바꾸면 그 선택을 존중한다. 베타 채널은 새 정식도 받을 수 있지만 정식으로 전환했다고 현재 앱을 즉시 낮추지는 않는다.

## Tether 적용안

### 1. 최종 버전 결정과 채널

- 최종 결정: `연도.월.배포순번`, 첫 후보 `2026.9.1-beta.1` / 빌드 42. 앞서 검토한 0.x 및 내부 빌드 초기화안은 채택하지 않았다.
- 앱 식별자·설정·보호 상태·서명키·schema 2·protocol 2를 유지한다.
- 내부 빌드는 모든 채널에서 계속 증가하고 베타 순번과 구분한다.
- 정식/베타가 함께 들어가는 고정 HTTPS 피드와 Sparkle 공식 채널 기능을 사용한다.
- 이전 피드 URL 환경설정만 정리한다. 사용자 설정 전체를 삭제하지 않는다.
- 더 높은 기능 버전 베타 뒤에 낮은 표시 버전 hotfix를 발행하는 순서는 피드 생성기에서 거부한다.

Sparkle는 채널과 표시 버전/비교용 버전을 지원한다. 새로운 구현은 피드를 매번 수동 전환하기보다 공식 채널 기능을 우선한다. [공식 채널 안내](https://sparkle-project.org/documentation/publishing/#channels), [버전 비교 권고](https://sparkle-project.org/documentation/upgrading/).

### 2. 다운로드와 앱 설정

다운로드 페이지에는 정식과 베타를 분리하고 버전·배포일·최소 macOS·칩·변경사항을 함께 표시한다. 아직 첫 정식이 없다면 존재하지 않는 정식 다운로드 버튼을 만들지 않고 ‘정식 준비 중’이라고 표시한다. GitHub의 옛 2.0.1 latest 링크가 새 계열의 정식 다운로드로 연결되지 않도록 한다.

앱 설정의 업데이트 영역은 다음으로 제한한다.

- 현재 버전과 Beta 표시. 내부 빌드는 세부 정보나 진단에서 확인.
- 업데이트 채널: 정식 / 베타 포함.
- 자동 확인: 기본 하루 한 번. 자동 다운로드·설치는 제공하지 않는다. 이는 Tether의 운영 기본값이며 다른 앱의 공통 표준을 뜻하지 않는다.
- 최근 확인 결과와 ‘업데이트 확인…’ 버튼.
- 새 버전이 있으면 변경사항, ‘다운로드 및 설치…’, 나중에 선택.
- 베타에서 정식 채널로 바꾼 상태라면 ‘다음 정식 버전부터 받습니다. 현재 베타는 유지됩니다.’라는 설명.

예약 검사는 갑자기 창을 앞으로 띄우지 않는다. 메뉴바 패널/앱 설정에 새 버전 표시를 남기고 사용자가 클릭하면 Sparkle 표준 창을 연다. 네트워크 오류는 ‘최신 버전’으로 표시하지 않는다. 별도의 자체 다운로드 엔진은 만들지 않는다. [Sparkle gentle reminders](https://sparkle-project.org/documentation/gentle-reminders/).

### 3. 클램쉘 작업을 고려한 설치

Tether의 정상 종료는 현재 유지 세션을 해제한다. 따라서 다른 앱의 ‘자동 설치’를 그대로 켜는 것은 부적절하다. 다음은 Tether 특성에서 도출한 추가 정책이다.

1. 업데이트 확인·선택적 다운로드는 작업 중에도 가능하다.
2. 덮개가 닫혀 있거나 현재 덮개 상태를 확인하지 못하면 앱/도우미 교체를 시작하지 않는다. 화면 잠금 여부만으로 안전한 상태라고 판단하지 않는다.
3. 덮개를 열고 사용자가 설치를 선택하면 전원 변경을 정리한 뒤 앱을 교체한다. 검사 이후 덮개를 다시 닫는 경합도 설치 직전에 재확인한다.
4. 새 앱 실행 후 필요한 관리자 도우미 갱신을 요청한다. 취소·실패면 ‘도우미 업데이트 필요’ 상태를 유지하고 제어를 시작하지 않는다.
5. 새 앱/도우미의 버전·빌드·프로토콜·실시간 응답과 설정 이관을 확인한 뒤 완료로 표시한다. 현재 코드의 검사 기반을 재사용한다.
6. 종료된 일회성 타이머를 업데이트가 되살리지 않는다. 기존 비활성 선택·보호 중지는 보존한다.

닫힌 상태에서 업데이트하기 위해 임시 전역 절전 방지를 더 거는 방식이나 watchdog을 끄는 방식은 사용하지 않는다. 도우미 없이 전원 관리가 이어진다고 안내하지도 않는다.

### 4. 실패와 이전 버전 복귀

서명 검증 실패·다운로드 실패는 현재 앱을 유지하고 원인을 표시한다. 앱 교체, 도우미 교체, 설정 이관의 성공 여부를 별도로 확인한다. 도우미 설치 단계의 기존 백업·복구 절차를 사용하되 전체 앱까지 자동 원복된다고 주장하지 않는다.

‘정식 채널로 변경’과 ‘이전 정식 즉시 재설치’는 다른 동작이다. 자동 다운그레이드는 제공하지 않는다. 즉시 복귀가 필요할 때만 이전 버전 다운로드와 설정 백업·호환성 안내를 제공한다. 업데이트 후 바뀐 설정을 옛 백업으로 조용히 덮어쓰지 않는다.

## 게시 순서

이 부분은 조사 결과에서 도출한 배포 운영안이다.

1. 소스 커밋과 CI 결과를 확정한다.
2. ZIP, 코드 서명/공증 상태, Sparkle 서명, 아키텍처, helper를 검증한다.
3. 불변 버전 URL에 파일을 올리고 공개 다운로드를 다시 받아 검사한다.
4. 검증된 파일을 가리키도록 서명된 고정 피드를 마지막에 갱신한다.
5. 이전 정식/베타 설치 fixture로 후보 선택과 실제 다운로드·교체를 검사한다.
6. 정식/베타 다운로드 링크도 같은 배포 메타데이터에서 생성해 피드와 엇갈리지 않게 한다.

버전별 ZIP을 덮어쓰거나 피드를 바이너리보다 먼저 게시하지 않는다. 혼자 사용하는 현재 단계에서는 nightly, 강제 업데이트, 복잡한 배포 비율 조절, 독자 업데이터는 제외한다. 서명키 교체나 공증은 버전 이름 초기화와 별개의 작업이다.

## 필요한 회귀 검사

| 상황 | 기대 결과 |
|---|---|
| 정식 사용자 + 더 새로운 베타만 있음 | 베타 설치 제안 없음 |
| 베타 사용자 + 새 베타 | 자동 검사와 수동 검사 모두 후보 발견 |
| 베타 → 같은 기능 버전의 새 정식 | 정식으로 정상 업데이트 |
| 채널 정식으로 변경 후 재실행 | 선택 유지, 베타 재구독 없음 |
| 설정에 남은 예전 피드/건너뛰기 값 | 날짜형 버전의 새 피드와 수동 검사가 정상 작동 |
| 내부 번호 유지 | 기존 41보다 높은 42부터 시작, 이후 모든 채널에서 증가 |
| 베타 뒤 구계열 정식 hotfix 게시 | 의도하지 않은 기능·설정 다운그레이드 없음 |
| 덮개 닫힘/확인 실패, 설치 직전 닫힘 | 교체 시작 보류, 현재 유지 중단 없음 |
| 다운로드/피드 변조, 네트워크 단절 | 현재 앱 유지, 오류 원인 표시 |
| 설치 중 사용자 취소·관리자 인증 취소 | 설치 단계별 미완료 상태 표시, 허위 완료 없음 |
| 도우미 시작 실패·다른 빌드·이관 실패 | 제어 차단, 가능한 기존 복구와 백업 보존 |
| 이관 후 사용자가 수정한 설정 | 재실행으로 과거 값에 덮어쓰기 없음 |

## 현재 코드와의 차이

2026.9.1 빌드 42에 채널 선택, gentle reminder, 덮개 상태 기반 설치 대기, 인증 후 도우미 설치 재검사, 고정 서명 피드·다운로드 목록 생성을 구현했다. 단위/SDK delegate/실제 Sparkle fixture/설치 스크립트 검증 결과는 이번 배포 보고서에 기록한다. 공개 피드 게시와 실제 사용자 앱 재시작·관리자 설치·물리 동작은 별도 검증 대상이다.


## 빌드 43 후속 확인

캐시된 후보 재개에서도 채널을 재확인하고, 준비된 설치 보류가 종료 후 설치 예약을 남기지 않도록 보완했다. 이전 다운그레이드 fixture는 동일 빌드였으므로 낮은 빌드 검사를 분리했다. 현재 검증 상태·환경 제한·미게시 상태는 [최신 보고서](VERSIONING-AND-UPDATE-REPORT.ko.md)를 따른다.
